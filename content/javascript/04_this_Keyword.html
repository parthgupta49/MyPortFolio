The this Keyword in JavaScript

Complete Revision Notes + Practice Sheet

Enriched with gotchas, mental models & interview patterns from hands-on practice

🧠 What is this?

Core Idea: The this keyword in JavaScript is a special keyword whose value is determined at RUNTIME. It is NOT fixed — it depends on HOW a function is called, not where it is written. This is what makes it one of the trickiest and most-asked interview topics.

It behaves differently in these contexts:

  1. Global Space
  2. Inside a Function (Strict vs Non-Strict Mode)
  3. Inside an Object's Method
  4. With call(), apply(), and bind()
  5. Inside Arrow Functions
  6. Inside DOM Elements
  7. Inside Classes & Constructors

1. this in Global Space

Rule: In the global space (outside any function), this always refers to the Global Object.

Global Space = any code written at the top level, outside any function or block.

console.log(this);  // In browser → window object
EnvironmentGlobal Object (value of this)
Browserwindow
Node.jsglobal
Web Workerself
Other JS RuntimesVaries
🎯 Interview Answer: "In the global space, this refers to the global object. It is window in browsers, global in Node.js, and can be different in other environments."

2. this Inside a Function (Strict vs Non-Strict Mode)

Rule: Inside a regular function, the value of this depends on strict mode.

ModeValue of this inside a function
Strict mode ("use strict")undefined
Non-strict mode (sloppy/default)window (global object)

Example — Strict Mode:

"use strict";
function x() {
  console.log(this);   // undefined
}
x();

Example — Non-Strict Mode:

// Non-strict mode (default)
function x() {
  console.log(this);   // window
}
x();

But WHY does non-strict mode give window instead of undefined?

Because of a mechanism called this Substitution ↓

3. this Substitution (Important Concept!)

Rule: If the value of this keyword is undefined or null, JavaScript REPLACES it with the global object — but ONLY in non-strict mode.

this === undefined or null
       ↓ (non-strict mode ONLY)
this → replaced with global object (window in browser)

In strict mode: NO substitution happens. undefined stays undefined.

🎯 Interview Tip: "The actual value of this inside a function is undefined. But in non-strict mode, due to this substitution, JavaScript replaces undefined with the global object."

4. this Depends on HOW the Function is Called

Golden Rule: Always ask yourself — "What object is calling this function?" That object becomes this. If NO object is calling it, this is undefined (strict) or window (non-strict via substitution).

"use strict";
function x() {
  console.log(this);
}

x();           // undefined → called without any object reference (naked call)
window.x();    // window    → called WITH window as the reference object
How CalledValue of this (strict mode)
x() — without reference (naked)undefined
window.x() — with referencewindow
🔑 Key Insight: The value of this is determined at runtime based on the calling context (runtime binding). MDN: "In most cases, the value of this is determined by how a function is called."

5. this Inside an Object's Method

Function vs Method — Know the Difference!

A function that is a property of an object is called a method.

const student = {
  name: "Rahul",
  printName: function() {
    console.log(this);        // → student object
    console.log(this.name);   // → "Rahul"
  }
};

student.printName();   // this = student (object LEFT of the dot)

Rule: When a method is called using obj.method(), the value of this inside the method is THAT object (obj).

⚠️ But what if you extract the method?

const extracted = student.printName;
extracted();   // this = window (non-strict) or undefined (strict)
               // Because it's now a "naked" call — no object to the left!

6. Explicitly Setting this — call(), apply(), and bind()

Purpose: These three methods allow you to explicitly set the value of this when calling a function. They are used to SHARE/REUSE methods across objects.

The Problem — Sharing Methods:

const student = {
  name: "Rahul",
  printName: function() {
    console.log(this.name);
  }
};

const student2 = { name: "Deepika" };
// student2.printName() → ❌ Error! printName doesn't exist on student2

The Solution — .call():

student.printName.call(student2);   // "Deepika" ✅
// Whatever you pass as the FIRST argument to .call() BECOMES the value of `this`.

Comparison Table — call vs apply vs bind:

MethodSyntaxInvokes Immediately?Arguments Format
call()fn.call(thisArg, arg1, arg2, ...)✅ YesComma-separated
apply()fn.apply(thisArg, [arg1, arg2])✅ YesArray
bind()fn.bind(thisArg, arg1, arg2)❌ No (returns new fn)Comma-separated
// call — invokes immediately, args comma-separated
student.printName.call(student2);

// apply — invokes immediately, args as array
student.printName.apply(student2, [arg1, arg2]);

// bind — returns a NEW function with `this` permanently bound
const boundFn = student.printName.bind(student2);
boundFn();   // "Deepika"
🎯 Interview Favourite: "call and apply invoke the function immediately; bind returns a new function with this permanently bound. The only difference between call and apply is how arguments are passed — comma-separated vs array."

7. this Inside Arrow Functions (⚡ Trickiest Part)

Rule: Arrow functions do NOT have their own this binding. They take the value of this from their ENCLOSING LEXICAL CONTEXT — i.e., the scope where the arrow function is physically written in the code.

🔑 3 Magic Words: ENCLOSING LEXICAL CONTEXT

Example 1 — Arrow function directly as a method (in an object):

const obj = {
  a: 10,
  x: () => {
    console.log(this);   // window (NOT obj!)
  }
};
obj.x();

// WHY window? The arrow function 'x' is written directly inside obj,
// and obj sits in the GLOBAL SPACE. So enclosing lexical context = global → this = window.

Example 2 — Arrow function nested inside a regular function (method):

const obj2 = {
  a: 20,
  x: function() {
    const y = () => {
      console.log(this);   // obj2 ✅
    };
    y();
  }
};
obj2.x();

// WHY obj2? Arrow fn 'y' is enclosed inside regular function 'x'.
// x's this (called as obj2.x()) = obj2. Arrow fn inherits that.
💡 Mental Model / Trick: "Pretend the arrow function doesn't exist. Whatever this would be at that location — THAT is the value of this for the arrow function."

Quick Reference — Arrow Function Scenarios:

Scenariothis value
Arrow fn directly in an object (method)Global object (window) — object's lexical parent is global
Arrow fn inside a regular function (method)The object that called the outer function
Arrow fn in global scopeGlobal object (window)

8. this Inside DOM Elements

Rule: When you use this inside an inline event handler in HTML, it refers to the HTML element itself that triggered the event.

<button onclick="alert(this)">Click Me</button>
<!-- alert → [object HTMLButtonElement] -->

<button onclick="alert(this.tagName)">Click Me</button>
<!-- alert → "BUTTON" -->
🎯 Interview Answer: "Inside DOM event handlers, this refers to the HTML element that received the event."

9. this Inside Classes & Constructors (Bonus)

class Student {
  constructor(name) {
    this.name = name;   // this = the new instance being created
  }
  greet() {
    console.log(`Hi, I'm ${this.name}`);
  }
}
const s = new Student("Parth");
s.greet();   // "Hi, I'm Parth"
  • Inside a constructor, this refers to the newly created instance.
  • Inside class methods, this refers to the instance the method is called on.
  • Classes in JS are ALWAYS in strict mode by default.

10. Closures & this — The Collision (Advanced)

Critical Insight: Closures capture VARIABLES (like let count, const name). Closures DO NOT capture the this keyword. Every time a regular function is called, the JS Engine generates a brand new this for it.

The Classic "Lost Context" Problem:

const user = {
  name: "Parth",
  createGreeter: function() {
    console.log("Outer this:", this.name);   // "Parth"

    return function innerGreeter() {
      console.log("Inner this:", this.name); // undefined (THE BUG!)
    };
  }
};

const greetFunction = user.createGreeter();   // "Outer this: Parth"
greetFunction();                               // "Inner this: undefined"

// WHY? innerGreeter was called as greetFunction() — naked call.
// JS Engine gives it a new `this` (window/undefined), ignoring user object.

Fix 1 — The Old School Hack (Pre-2015): The self Trick:

const user = {
  name: "Parth",
  createGreeter: function() {
    const self = this;   // Save `this` into a normal variable!

    return function innerGreeter() {
      console.log("Inner says:", self.name);   // "Parth" ✅
      // Closure captures 'self' (a variable), not 'this' (a keyword)!
    };
  }
};

Fix 2 — The Modern Fix (Post-2015): Arrow Functions:

const user = {
  name: "Parth",
  createGreeter: function() {
    return () => {
      console.log("Inner says:", this.name);   // "Parth" ✅
      // Arrow fn has no own `this`. Looks up to createGreeter's `this`.
    };
  }
};

Summary:

  • Regular Function: "I don't care about closures. Give me a new this based on how I am called right now."
  • Arrow Function: "I don't have my own this. I will use the closure to remember my parent's this."

⚙️ 10.5 — WHY Arrow Functions Don't Have Their Own this — The Engine-Level Explanation

🧠 This section answers the "WHY" — not just the rule, but what the JavaScript Engine actually does internally when it encounters this in regular vs arrow functions. Understanding this transforms your knowledge from memorized rules to deep engine-level intuition.

The Answer Lives Inside the Execution Context

Every time a function is called, the JS Engine creates an Execution Context. That Execution Context has three components:

┌─────────────────────────────────────┐
│        EXECUTION CONTEXT            │
│                                     │
│  1. Variable Environment            │
│     (let, const, var declarations)  │
│                                     │
│  2. Lexical Environment             │
│     (Scope Chain → parent ref)      │
│                                     │
│  3. this Binding    ← THIS IS KEY   │
│     (determined at call time)       │
│                                     │
└─────────────────────────────────────┘

That third component — the this Binding — is where the entire mystery lives.

🟢 Regular Function — Engine CREATES a Fresh this Binding Every Time

When the engine encounters a regular function call, it does the following before executing a single line of code:

  1. Creates a new Execution Context
  2. Asks: "HOW is this function being called?" and determines the this binding based on the call-site
  3. Stuffs that this value into the Execution Context
  4. Only then starts executing the function's code
const obj = {
  value: 42,
  outer: function() {
    console.log("Outer:", this.value);   // 42

    function inner() {
      console.log("Inner:", this.value); // undefined!
    }
    inner();
  }
};
obj.outer();

The engine creates TWO separate, independent Execution Contexts:

CALL: obj.outer()
┌─────────────────────────────────────┐
│   Execution Context of outer()      │
│                                     │
│   Variable Environment: { inner }   │
│   Lexical Environment: → global     │
│   this Binding: obj  ✅             │
│   (because: obj.outer() → dot rule) │
└─────────────────────────────────────┘

CALL: inner()   ← naked call!
┌─────────────────────────────────────┐
│   Execution Context of inner()      │
│                                     │
│   Variable Environment: { }         │
│   Lexical Environment: → outer      │
│   this Binding: window  ✅ NEW ONE! │
│   (because: inner() → naked call)   │
└─────────────────────────────────────┘
🔑 Critical Point: The engine created a brand new, independent this binding for inner(). It did NOT look at outer's this. It didn't care. It only asked: "How is inner being called RIGHT NOW?" — answer: naked → this = window. Every regular function call triggers a fresh this binding creation. The engine never inherits, never copies, never looks up the parent's this.

⚡ Arrow Function — Engine SKIPS this Binding Creation Entirely

const obj = {
  value: 42,
  outer: function() {
    const inner = () => {
      console.log(this.value);   // 42!
    };
    inner();
  }
};
obj.outer();

Here's the critical difference. When the engine creates the Execution Context for the arrow function:

CALL: obj.outer()
┌─────────────────────────────────────┐
│   Execution Context of outer()      │
│                                     │
│   Variable Environment: { inner }   │
│   Lexical Environment: → global     │
│   this Binding: obj  ✅             │
└─────────────────────────────────────┘

CALL: inner()  (arrow function)
┌─────────────────────────────────────┐
│   Execution Context of inner()      │
│                                     │
│   Variable Environment: { }         │
│   Lexical Environment: → outer      │
│   this Binding: ❌ DOES NOT EXIST   │
│   (arrow fn → engine SKIPS this!)   │
└─────────────────────────────────────┘
The engine literally does not create a this binding. It's not that it sets it to something special. It's not that it copies the parent's. The slot simply doesn't exist.

So What Happens When Code References this?

When the engine encounters this.value inside the arrow function:

  1. Looks in current Execution Context for this → ❌ NOT FOUND
  2. Since it's not found, the engine does what it always does when it can't find something — it goes up the scope chain (Lexical Environment)
  3. It reaches outer()'s Execution Context → finds this = obj → ✅ FOUND!
  4. Uses obj.value = 42
🧠 THE BREAKTHROUGH INSIGHT: Inside an arrow function, this behaves exactly like a regular variable. Just like how if you reference a variable x and it's not declared in the current scope, the engine walks up the scope chain to find it — the exact same mechanism applies to this in arrow functions.

🤔 But WHY Was It Designed This Way?

This isn't random. Arrow functions were added in ES6 (2015) specifically to solve the "lost this" problem that tortured developers for 15+ years.

Before 2015, developers had to write ugly hacks:

// The "self" hack — saving `this` into a variable
const self = this;
setTimeout(function() {
  console.log(self.name);   // use the variable instead of `this`
}, 100);

The TC39 committee (the people who design JavaScript) essentially said:

💡 Design Decision: "What if we create a function type that doesn't generate its own this at all? Then this would naturally flow through the scope chain, just like variables do. No more hacks needed."

And that's exactly what arrow functions are — functions with no this binding mechanism. They're not "inheriting" or "copying" anything. The slot simply doesn't exist, and the scope chain does the rest automatically.

🎯 Thought Experiment: arguments Works The Same Way

The exact same principle applies to arguments. Regular functions have their own arguments object. Arrow functions don't:

function outer() {
  console.log(arguments);   // [1, 2, 3] ✅ has its own

  const inner = () => {
    console.log(arguments); // [1, 2, 3] ← inherited from outer via scope chain!
  };
  inner(4, 5, 6);  // still prints [1, 2, 3], NOT [4, 5, 6]
}
outer(1, 2, 3);
Pattern: Arrow functions don't have their own this, don't have their own arguments, don't have their own super, and can't be used as constructors with new. They're intentionally lightweight — designed to be transparent windows into their parent's execution context.

🗣️ How to Explain This in an Interview

"The reason arrow functions don't have their own this is rooted in how the JavaScript engine creates Execution Contexts. For a regular function, the engine always creates a fresh this binding as part of the Execution Context, determined by the call-site. For an arrow function, the engine skips the this binding step entirely — the slot doesn't exist in the Execution Context. So when this is referenced inside an arrow function, the engine treats it like any other variable and resolves it via the scope chain, walking up to the nearest enclosing regular function that has a this binding. This is why arrow functions 'inherit' this — they're not copying it, they're simply looking it up through the same mechanism used for variable resolution."

11. Common Gotchas — Mistakes You WILL Make

These gotchas are sourced from actual mistakes made during practice sessions. Each one represents a real conceptual trap.

Gotcha A: ReferenceError vs undefined vs TypeError

ExpressionResultWhy
console.log(xyz)❌ ReferenceErrorVariable xyz was never declared
console.log(obj.xyz)undefined (no error)obj exists, property doesn't
console.log(window.brand)undefined (no error)window exists, brand doesn't
console.log(undefined.age)💥 TypeErrorCannot read properties of undefined
console.log(null.age)💥 TypeErrorCannot read properties of null
Memory Aid:
• ReferenceError → accessing an UNDECLARED VARIABLE
• undefined → accessing a NON-EXISTENT PROPERTY on an object
• TypeError → accessing a property on undefined or null ITSELF 
"use strict";
function x() {
  console.log(this);        // undefined (this itself is undefined)
  console.log(this.name);   // 💥 TypeError! (undefined.name)
}
x();  // naked call in strict mode

Gotcha B: Arrow Function's this = IMMEDIATE Enclosing Context

❌ Wrong mental model: "Arrow function traverses up the scope chain to find a useful this."

✅ Correct mental model: "Arrow function takes this from its IMMEDIATE enclosing regular function. If that parent's this is undefined, the arrow fn's this is also undefined. It does NOT skip over." 
"use strict";
const obj = {
  value: 42,
  level1: function() {
    console.log("L1:", this.value);    // 42 ✅ (obj.level1() → this = obj)

    function level2() {
      console.log("L2:", this.value);  // 💥 TypeError (naked call → this = undefined)

      const level3 = () => {
        console.log("L3:", this.value); // Would also be TypeError
      };                                // (inherits level2's undefined)
      level3();  // Never executes — L2 already crashed
    }
    level2();   // naked call!
  }
};
obj.level1();

// L3 does NOT skip level2 and grab level1's `this`.
// Arrow fn inherits from IMMEDIATE parent only.

Gotcha C: setTimeout Does NOT Change Lexical Context

Rule: setTimeout is just a delivery mechanism. It decides WHEN the function runs, not what this is.

const app = {
  title: "MyApp",
  init: function() {                // app.init() → this = app

    setTimeout(function() {
      console.log("A:", this.title);  // undefined (regular fn → this = window)
    }, 100);

    setTimeout(() => {
      console.log("B:", this.title);  // "MyApp" ✅ (arrow fn → inherits from init)
    }, 200);
  }
};
app.init();

Gotcha D: return Does NOT Change Arrow Function's this

Rule: Arrow function returns can be called later, but this is locked in at the time of its creation (where it was written).

const factory = {
  product: "Phone",
  make: function() {
    console.log("1:", this.product);   // "Phone"

    return {
      product: "Laptop",
      build: function() {
        console.log("2:", this.product);  // "Laptop"

        return () => {
          console.log("3:", this.product); // "Laptop" ✅ (inherits from build)
        };
      }
    };
  }
};

const item = factory.make();    // 1: "Phone"
const buildFn = item.build();   // 2: "Laptop"
buildFn();                       // 3: "Laptop" (NOT undefined!)

Gotcha E: call() / apply() / bind() Cannot Override Arrow Functions

const sayHi = () => {
  console.log(this.name);
};

const user = { name: "Parth" };
sayHi.call(user);   // Does NOT print "Parth"
                     // call() is IGNORED for arrow functions!

Gotcha F: window.name is a Built-in Browser Property

Quirk: window.name is a built-in browser property that defaults to "" (empty string). Other properties like .title, .brand, etc. will return undefined.

console.log(window.name);     // "" (built-in, always exists)
console.log(window.title);    // undefined
console.log(window.brand);    // undefined

13. The Ultimate Flow — How To Solve ANY this Question

Step 1: Is it an Arrow Function?
  → YES → Look at the nearest enclosing regular function. That function's this is your this.
  → NO → Go to Step 2.

Step 2: How is the Regular Function Called?
  → obj.fn() → this = obj
  → fn() naked → this = window (non-strict) or undefined (strict)
  → fn.call(x) / fn.apply(x) → this = x
  → new fn() → this = newly created object

Step 3: What is this Right Now?
  → An object → .property = value or undefined
  → undefined or null → .property = 💥 TypeError!

14. Interview Answer Template

If the interviewer asks: "Explain the this keyword in JavaScript"

"The this keyword in JavaScript is not fixed. Its value is determined at runtime based on how a function is called. In the global space, it refers to the global object. Inside a regular function, it is undefined in strict mode, but in non-strict mode, JavaScript performs this substitution and replaces undefined with the global object. Inside an object's method, this refers to the calling object. Arrow functions don't have their own this — they inherit it from their enclosing lexical context. And we can explicitly control this using call, apply, or bind. Closures capture variables but NOT the this keyword — which is why the self trick or arrow functions are used to preserve context in nested functions."

Key Takeaways

  • this is about HOW a function is called, not WHERE it is written.
  • Closures capture variables, NOT this.
  • Arrow functions solve the "lost this" problem by inheriting from enclosing lexical context.
  • this substitution only happens in non-strict mode (undefined/null → global object).
  • ReferenceError ≠ undefined ≠ TypeError — know the difference!
  • At the engine level: Regular functions CREATE a this binding; Arrow functions DON'T — they resolve this via scope chain like a variable.
