1. What is Currying?

▼
Definition: Currying is a technique that transforms a function taking multiple arguments into a sequence of nested functions, each taking a single argument (or a subset). Instead of calling fn(a, b, c), you call fn(a)(b)(c).

Normal vs Curried — Side by Side:

// NORMAL — all arguments at once
function multiply(a, b, c) {
  return a * b * c;
}
multiply(2, 3, 4);      // 24

// CURRIED — one argument at a time
function curriedMultiply(a) {
  return function(b) {
    return function(c) {
      return a * b * c;
    };
  };
}
curriedMultiply(2)(3)(4);   // 24

The Same Thing With Arrow Functions:

const curriedMultiply = a => b => c => a * b * c;

curriedMultiply(2)(3)(4);   // 24

Read the arrows left-to-right: "take a, return a function that takes b, which returns a function that takes c, which returns a * b * c."

🔑 The key difference: With a normal function you must supply ALL arguments at once. With a curried function, you can supply them one at a time, across separate calls, and the function "remembers" the earlier ones until it has everything it needs.

2. It's Just Closures (Don't Overthink It)

▼
🧠 The honest truth: Currying is not some deep new concept. It is closures, used one level deeper. If you understand closures (Chapter 3), you already understand currying. The only "new" thing is the syntax.

Why It Works — The Closure Chain:

const add = a => b => a + b;

const add5 = add(5);   // add(5) runs, `a` is set to 5
                       // it returns the inner fn: b => 5 + b
                       // the inner fn CLOSES OVER a = 5

add5(3);   // 8   — inner fn remembers a=5 via closure, adds b=3

Step-by-Step Memory Trace:

const add5 = add(5);

// 1. add(5) executes. `a = 5` in its scope.
// 2. It returns `b => a + b`.
// 3. add()'s execution context is DESTROYED...
//    ...but the returned function kept a CLOSURE over `a = 5`.

CLOSURE OF add5:
┌──────────────┐
│  a: 5        │  ← preserved from add's dead scope
└──────────────┘
       ↑
     add5  ── when called with 3 → returns 5 + 3 = 8
💡 If someone asks "how does currying work?" — the answer is one word: closures. Each returned function closes over the arguments passed to the functions before it.

3. Two Ways to Curry — Closures & bind()

▼

There are two ways. Both achieve the same thing.

Method 1 — Closures (the common way)

const multiply = x => y => x * y;

const multiplyByTwo = multiply(2);    // x locked to 2 via closure
multiplyByTwo(5);                      // 10

const multiplyByThree = multiply(3);
multiplyByThree(10);                   // 30

Method 2 — Using bind()

Remember bind() from Chapter 4? It returns a NEW function with some arguments pre-set. That's currying too.

const multiply = function(x, y) {
  return x * y;
};

// bind(this, 2) pre-sets the FIRST argument (x) to 2:
const multiplyByTwo = multiply.bind(this, 2);

multiplyByTwo(5);   // 10  — 5 becomes y, x is already 2

bind() Edge Cases (worth knowing):

CodeResultWhy
multiply.bind(this, 2)(5)10x=2 preset, y=5 at call
multiply.bind(this, 2, 3)(5)6Both x=2, y=3 preset. The 5 is ignored.
multiply.bind(this)(2, 3)6Nothing preset, both passed at call

Comparison:

Closure methodbind() method
MechanismNested functions + scopeEngine pre-sets arguments
Call stylefn(2)(5)fn.bind(this, 2)(5)

Most common?✅ YesRare in practice

4. Partial Application (Cousin of Currying)

▼

These two terms get confused constantly. Here's the honest, simple distinction:

TermMeaning
CurryingTransform fn(a, b, c) into fn(a)(b)(c) — one arg per call, strictly
Partial ApplicationPre-fill SOME arguments now, supply the REST later. fn(a, b) then partial(c)
// PARTIAL APPLICATION — pre-fill some, supply rest later
function greet(greeting, name) {
  return `${greeting}, ${name}!`;
}

const sayHello = greet.bind(this, "Hello");   // pre-fill greeting
sayHello("Parth");     // "Hello, Parth!"
sayHello("Deepika");   // "Hello, Deepika!"
💡 Don't stress the distinction. In everyday conversation, people use "currying" loosely to mean both. The practical idea is the same: lock in some arguments now, provide the rest later, and reuse the specialized function.

⚠️ 5. When Currying Is USELESS (Trust Your Instinct)

▼
Your skepticism is valid engineering taste. Most tutorials oversell currying. Here's when it's genuinely pointless — and rejecting it in these cases makes you a BETTER engineer, not a worse one.

❌ Useless Case 1 — Currying just to show off

// Pointless. Just write add(1, 2, 3).
const add = a => b => c => a + b + c;
add(1)(2)(3);   // 6

// If you always have all 3 arguments at call-time,
// currying adds NOTHING but confusion. Use a normal function.

❌ Useless Case 2 — When you never reuse the partial

// If you only ever call it once with all args, currying is wasted:
const multiply = x => y => x * y;
multiply(4)(5);   // 20  — why not just multiply(4, 5)?

// Currying only pays off if you REUSE the intermediate function.
🎯 The rule: If you're going to supply all arguments at the same moment, and you won't reuse a partially-applied version — do NOT curry. A normal function is clearer, faster to read, and easier to debug. Choosing the simpler tool is a sign of maturity, not ignorance.

✅ 6. When Currying Is ACTUALLY Useful

▼

Three real cases where currying earns its place. Notice the common thread: you create a specialized function once, then reuse it.

✅ Use Case 1 — Specialized reusable functions

const isDivisibleBy = divisor => num => num % divisor === 0;

const isEven = isDivisibleBy(2);        // reusable!
const isMultipleOf5 = isDivisibleBy(5);

[1,2,3,4,5,6].filter(isEven);           // [2, 4, 6]
[5,10,12,15,20].filter(isMultipleOf5);  // [5, 10, 15, 20]

// Cleaner than writing `n => n % 2 === 0` over and over.

✅ Use Case 2 — Reusable filters (your build task!)

const filterBy = key => value => arr =>
  arr.filter(item => item?.[key] === value);

const filterEngineers = filterBy("role")("engineer");
const filterManagers  = filterBy("role")("manager");

filterEngineers(users);   // all engineers
filterManagers(users);    // all managers

// You built the filter logic once. Now spin up specialized
// filters on demand. This is currying doing real work.

✅ Use Case 3 — Configuration set once, reused many times

const createLogger = prefix => message =>
  console.log(`[${prefix}] ${message}`);

const errorLog = createLogger("ERROR");
const infoLog  = createLogger("INFO");

errorLog("Database down");    // [ERROR] Database down
infoLog("Server started");    // [INFO] Server started
🔑 The common thread: In every useful case, you lock in a configuration once (the divisor, the key, the prefix) and reuse the specialized function many times. That reuse is what justifies currying. No reuse = don't curry.

7. Currying in React (Where You'll Actually Meet It)

▼
⭐ THIS is the moment currying will click for you — not in a contrived add(1)(2)(3), but in real React code. When you reach Week 5-7 of your roadmap, you'll write this pattern without even thinking about it.

The Classic React Pattern — Event Handler With an Argument:

// A curried event handler:
const handleDelete = (id) => (event) => {
  console.log("Deleting item", id);
  // ...delete logic
};

// In JSX — rendering a list of delete buttons:
{items.map(item => (
  <button onClick={handleDelete(item.id)}>
    Delete
  </button>
))}

Why Currying Is Needed Here:

The onClick handler automatically receives the event object. But you ALSO need to know WHICH item's button was clicked (the id).

  • handleDelete(item.id) runs during render — it locks in the id and returns the actual handler.
  • When the button is clicked later, React calls that returned handler with the event.
  • The returned handler remembers id via closure. 🎯
⚠️ Common beginner mistake: 
// ❌ WRONG — calls handleDelete IMMEDIATELY during render:
<button onClick={handleDelete(item.id)}>   // only works if curried!

// ❌ WRONG — passing args the naive way runs it on every render:
<button onClick={handleDelete(item.id, event)}>   // event undefined here

// ✅ RIGHT — either curry (above) or wrap in arrow:
<button onClick={(e) => handleDelete(item.id, e)}>
Both the curried version and the arrow-wrap version work. You'll see both in real codebases.
💡 Bottom line: You don't need to force currying into your own code now. But when React hands you this event-handler situation, you'll recognize it — and it'll finally feel useful instead of academic.

9. Interview Answer Templates

▼

Q: "What is currying?"

"Currying is a technique that transforms a function taking multiple arguments into a sequence of functions that each take a single argument. So instead of fn(a, b, c), you call fn(a)(b)(c). It works entirely through closures — each returned function remembers the arguments passed to the functions before it. You can implement it with nested functions or using bind()."

Q: "How does currying work under the hood?"

"Through closures. When the outer function is called with the first argument, it returns an inner function that closes over that argument. Even after the outer function's execution context is destroyed, the inner function retains access to that argument via the closure. This chains all the way down until all arguments are collected and the final result is computed."

Q: "When would you actually use currying?"

"When I want to create specialized, reusable functions by locking in some configuration up front. For example, a filterBy(key)(value) function lets me build specific filters like 'filter by role engineer' once and reuse them. In React, curried event handlers are common — like onClick={handleDelete(id)} — where I lock in the item id and the handler receives the event later. But I wouldn't curry if I always have all arguments at once and won't reuse the partial — a normal function is clearer there."
🎯 Interview power move: Mentioning that you know when NOT to curry signals maturity. Junior devs overuse patterns; senior devs know the tradeoffs. Saying "I wouldn't curry here because there's no reuse" is more impressive than blindly currying everything.

Q3 — Answer

Explanation: double = multiply.bind(this, 2) presets x=2. double(10) → 2×10 = 20. preset = multiply.bind(this, 4, 5) presets BOTH x=4 and y=5. So preset(99) → 4×5 = 20. The 99 is ignored because both parameters were already filled by bind — there's no third parameter for 99 to land in.

Q4 — Answer

Snippet A — POINTLESS. All arguments are available at call time (sum(3)(4)), and the result is used once with no reuse of a partial. This should just be const sum = (a, b) => a + b; sum(3, 4);. Currying adds only confusion here.

Snippet B — JUSTIFIED. greaterThan(18) creates a reusable over18 predicate that reads cleanly and could be reused across multiple filters. Locking in the config (18) and reusing the specialized function is exactly when currying earns its place.

Q5 — Answer

// Readable version:
const filterBy = function(key) {
  return function(value) {
    return function(arr) {
      return arr.filter(item => item?.[key] === value);
    };
  };
};

// Arrow version (same thing):
const filterBy = key => value => arr =>
  arr.filter(item => item?.[key] === value);

Explanation: Three nested functions. filterBy("role") locks the key, ("engineer") locks the value, and the final call receives the array and does the filtering. The ?.[key] optional chaining safely handles objects missing that key. This is currying doing genuine work — you can now build filterEngineers, filterManagers, etc. and reuse them.

← Back to Question 5

Q6 — Answer

1) handleClick(42) runs during render — React evaluates it while building the JSX. It locks in id = 42 and returns the inner function.

2) The inner function (the one that logs) runs on click — React stores it as the click handler and calls it with the event when the user clicks.

3) Via closure. When handleClick(42) ran, the returned inner function closed over id = 42. Even though handleClick's execution finished during render, the inner function preserved id and can access it whenever the click eventually fires.

🔹 Currying = closures with fancier syntax. Nothing more.

🔹 fn(a)(b)(c) — each call locks one arg via closure

🔹 USELESS if all args available + no reuse → use a normal function

🔹 USEFUL for reusable specialized functions (filters, loggers, React handlers)
