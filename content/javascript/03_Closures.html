1. What is a Closure? — The Formal Definition

▼
A closure is a function bundled together (enclosed) with its lexical environment.

In simpler terms: A closure is when an inner function has access to the outer (enclosing) function's variables — even after the outer function has completely finished executing and its Execution Context has been destroyed.

From MDN: "A closure is the combination of a function and the lexical environment within which that function was declared."

The Simplest Closure:

function outer() {
  let a = 7;

  function inner() {
    console.log(a);   // inner "closes over" variable a
  }

  return inner;
}

let z = outer();   // outer() executes, returns inner, then outer's EC is DESTROYED
z();               // Output: 7 — But how? outer is long gone!

What just happened?

  1. We called outer(). It declared a = 7 and returned the function inner.
  2. Once outer() finished, its Execution Context was entirely destroyed and removed from the Call Stack.
  3. We later invoked z() (which holds inner).
  4. Even though outer is long gone, z() perfectly prints 7.
🔑 Why? Because when functions are returned in JavaScript, they are not returned alone. They are returned along with their lexical scope. When inner was born (defined) inside outer, the JS engine attached a hidden reference — inner.[[Scope]] — pointing to outer's lexical environment. When inner was returned and outer died, that reference kept the variables alive. This hidden reference IS the closure.

2. The Two Conditions for a Closure

▼
🧠 "When exactly IS a closure formed?" — This section answers the most common confusion.

A closure is formed when BOTH of these conditions are true:

#ConditionWhat It Means
1A function is defined inside another scopeThe inner function is physically written inside an outer function/block
2It references variables from that outer scopeThe inner function actually USES a variable that's not in its own local memory

✅ Closure — Both conditions met:

function outer() {
  let a = 7;              // outer's variable

  function inner() {
    console.log(a);       // ✅ references outer's variable
  }

  return inner;
}
// Condition 1: inner defined inside outer ✅
// Condition 2: inner uses 'a' from outer ✅
// → CLOSURE: YES

❌ NOT a closure — Condition 2 missing:

function outer() {
  let a = 7;

  function inner() {
    console.log("Hello"); // ❌ does NOT use any outer variable
  }

  return inner;
}
// Condition 1: inner defined inside outer ✅
// Condition 2: inner doesn't use any outer variable ❌
// → CLOSURE: NO (nothing meaningful to close over)

✅ Closure — Even without return:

function outer() {
  let a = 7;

  function inner() {
    console.log(a);       // ✅ uses outer's variable
  }

  inner();                // called directly, NOT returned
}
// Condition 1 ✅, Condition 2 ✅ → CLOSURE: YES (return is irrelevant)

✅ Closure — setTimeout callback:

function outer() {
  let a = 7;

  setTimeout(function() {
    console.log(a);       // ✅ anonymous fn uses outer's variable
  }, 1000);
}
// Condition 1: anonymous fn defined inside outer ✅
// Condition 2: it uses 'a' from outer ✅
// → CLOSURE: YES
💡 The simplest way to check: Does your function use a variable that it didn't create itself? And is that variable in a parent scope (not its own local memory)? If yes to both → that's a closure.

3. First-Class Functions — Why Closures Are Possible

▼

Closures exist because JavaScript treats functions as first-class citizens:

  • Functions can be assigned to variables: const fn = function() {}
  • Functions can be passed as arguments to other functions
  • Functions can be returned from other functions

All three of these allow a function to "travel" outside its birthplace — carrying its closure with it.

// Passing a function as an argument (callback pattern)
function execute(fn) {
  fn();
}

function greet() {
  let msg = "Hello";
  execute(function() {
    console.log(msg);   // Closure! This anonymous fn closes over msg
  });
}

greet();   // "Hello"

Local: { } ← inner's own memory (empty)

5. Closures Capture References, Not Snapshots

▼
Critical Rule: A closure does NOT store a snapshot of the value at the exact moment the function is declared. Instead, closures store the memory reference to the variables. By the time the closure is executed, it looks up the current value at that memory reference. 
function create() {
  let a = 10;

  function modify() {
    a = 100;
  }

  function read() {
    console.log(a);
  }

  modify();       // a is changed to 100
  return read;    // read closes over the REFERENCE to a
}

const reader = create();
reader();   // 100 (NOT 10!)
// The closure sees the CURRENT value of a, not the value when read was defined.

This also means closures see changes made AFTER they're created:

function counter() {
  let count = 0;

  return function() {
    count++;              // modifies the same variable via reference
    console.log(count);
  };
}

const fn = counter();
fn();   // 1
fn();   // 2 (not 1 again! count persists because it's a reference)
fn();   // 3
⚠️ Why this matters: This "reference not snapshot" behavior is exactly what causes the famous setTimeout + loop bug. The closure captures the reference to var i, and by the time the setTimeout fires, i has already been mutated to its final value.

6. Closures Beyond return — Callbacks, setTimeout, Event Handlers

▼
🔴 The #1 misconception about closures: Many people think closures only happen when you return a function. This is WRONG. return doesn't create the closure — it just makes it visible outside. The closure is formed the moment the inner function is DEFINED.

A closure is formed whenever a function is defined inside another scope and references that scope's variables. The delivery method is irrelevant:

Delivery MethodExampleClosure?
📦 Returnedreturn inner;✅ YES
📬 Passed as callbacksetTimeout(inner, 1000);✅ YES
🔔 Event handlerbtn.addEventListener('click', inner);✅ YES
📌 Assigned to outer varglobalVar = inner;✅ YES
▶️ Called directlyinner();✅ YES (if it references outer vars)

Proof — No return, still a closure:

function outer() {
  let count = 0;

  function inner() {
    count++;
    console.log(count);
  }

  inner();   // ← called directly, NOT returned
  inner();
}

outer();   // Output: 1, 2
// inner accessed count from outer's scope. That's a closure.
// No return was needed.

Proof — Passing to setTimeout, still a closure:

function setup() {
  let message = "Hello";

  setTimeout(function() {       // anonymous function DEFINED inside setup
    console.log(message);       // REFERENCES setup's variable
  }, 1000);                     // PASSED to setTimeout (not returned)
}

setup();   // setup() finishes instantly. EC destroyed.
// After 1 second: "Hello" — closure kept message alive!

Proof — Event handler, still a closure:

function attachHandler() {
  let clickCount = 0;

  document.getElementById("btn").addEventListener("click", function() {
    clickCount++;                      // references outer variable
    console.log("Clicked " + clickCount + " times");
  });
}

attachHandler();   // finishes instantly. But clickCount lives on via closure.
// Click 1: "Clicked 1 times"
// Click 2: "Clicked 2 times"
// Click 3: "Clicked 3 times"
🎯 The rule: The closure exists from the moment the function is born. How it "leaves" (return, callback, event handler, direct call) is irrelevant. The [[Scope]] reference is attached at creation time.
Stage 1 of 5
Stage 1: The pattern you know — outer returns inner.
Your comfort zone. outer() creates a variable, defines an inner function that uses it, and returns that inner function. The inner function carries a closure over secret.
function outer() {
  let secret = "Parth";        // outer's variable

  function inner() {            // inner function
    console.log(secret);        // accesses outer's variable
  }

  return inner;                 // delivery method: RETURN
}

const fn = outer();
fn();   // "Parth"
Stage 2: Instead of returning, PASS the inner function to someone else.
The closure is identical. The only thing that changed is the "delivery method" — we're handing the function to executeItLater() instead of returning it.
function outer() {
  let secret = "Parth";

  function inner() {
    console.log(secret);        // still accesses outer's variable!
  }

  executeItLater(inner);        // delivery method: PASS AS ARGUMENT
}

function executeItLater(callback) {
  callback();   // "Parth" — closure still works!
}

outer();
Same closure, different delivery. Whether you return it or pass it — the function still remembers its birthplace.
Stage 3: What if "executeItLater" is... setTimeout?
setTimeout is just a function that takes a callback and calls it later. It's EXACTLY like executeItLater from Stage 2.
function outer() {
  let secret = "Parth";

  function inner() {
    console.log(secret);
  }

  setTimeout(inner, 1000);     // delivery method: PASS TO setTimeout
}

outer();
// After 1 second: "Parth"
🔑 setTimeout is just another function that receives your callback. It's not magic. The closure was already formed when inner was defined.
Stage 4: Use an anonymous function inline.
Instead of defining inner separately, define it directly inside the setTimeout call. Same closure.
function outer() {
  let secret = "Parth";

  setTimeout(function() {       // anonymous fn defined RIGHT HERE
    console.log(secret);        // still accesses outer's variable!
  }, 1000);
}

outer();
// After 1 second: "Parth"
// Identical to Stage 3. Just no name for the inner function.
Stage 5: Replace "outer" with a for loop. THIS is the setTimeout + loop code.
The loop body is the "outer scope". The callback is the "inner function". The loop variable is the "variable being closed over". Same pattern as Stage 1.
// The "outer" is now the for loop body
// The "inner" is the anonymous callback inside setTimeout
// The "secret" is the loop variable i

for (var i = 1; i <= 3; i++) {
  setTimeout(function() {       // THIS is the "inner function"
    console.log(i);             // THIS is accessing the "outer variable"
  }, i * 1000);                 // THIS is "passing to someone else"
}

// The anonymous function inside setTimeout is defined inside the loop body.
// It references 'i' from the outer scope. That's a CLOSURE.
🔴 var: ONE i shared → all callbacks see final value (4)
🟢 let: NEW i per iteration → each callback sees its own value (1,2,3)

⚙️ 7. Scope Chain vs Closure — The Key Distinction

▼
They're NOT two different mechanisms. Closure IS the scope chain... that survives death.

Example 1 — Scope Chain (parent ALIVE):

function outer() {
  let a = 10;

  function inner() {
    console.log(a);    // a is not in inner's local memory
  }

  inner();   // called while outer is STILL RUNNING
}
outer();
Call Stack when inner() runs:
┌──────────┐
│  inner() │  ← currently running. Needs 'a'. Not in local memory.
├──────────┤
│  outer() │  ← STILL ALIVE on the stack! Has a = 10 in its memory.
├──────────┤
│   GEC    │
└──────────┘

→ Engine walks up scope chain → finds a = 10 in living parent → done.
→ Nothing special. Just normal scope chain lookup. Parent is alive.

Example 2 — Closure (parent DEAD):

function outer() {
  let a = 10;

  function inner() {
    console.log(a);
  }

  return inner;   // inner leaves, outer is about to die
}

const fn = outer();   // outer finishes → EC DESTROYED
fn();                  // calling inner... but outer is DEAD!
Call Stack when fn() runs:
┌──────────┐
│   fn()   │  ← currently running. Needs 'a'. Not in local memory.
├──────────┤
│   GEC    │  ← outer() is NOT HERE. It's dead. Gone. Popped off.
└──────────┘

Where is outer()? NOWHERE. Its EC was destroyed.
Its local memory (where a = 10 lived) should be GONE.

But fn() still prints 10. HOW?!

Because fn has a hidden [[Scope]] reference:
fn.[[Scope]] → { a: 10 }   ← THIS is the CLOSURE
                              outer's variables, preserved after death
🧠 The Summary:

Scope Chain = the mechanism — "if variable not here, look at parent, then grandparent, etc."

Closure = the preservation — "even if the parent is dead, the inner function keeps its variables alive through a hidden [[Scope]] reference"

Without closures, the scope chain only works while the parent is alive on the Call Stack. With closures, the scope chain works forever — even after the parent is dead and gone. They're the same mechanism. Closure just extends it beyond death. 
Analogy:

  Scope Chain = the ROAD between your house and the store.
                You walk the road to get groceries.

  Closure     = the store was supposed to be DEMOLISHED (parent EC destroyed),
                but because you still need groceries (inner fn references variables),
                the store was PRESERVED just for you.

                The road (scope chain) still exists.
                The store (parent's variables) was kept alive BY the closure.
                Without the closure, the store would be gone and the road
                would lead to nothing (ReferenceError).

8. Independent Closures — Same Factory, Different Memory

▼ 
function counter() {
  let count = 0;
  return function() {
    count++;
    return count;
  };
}

const counterA = counter();   // Fresh EC → fresh count = 0
const counterB = counter();   // Another fresh EC → another fresh count = 0

console.log(counterA());   // 1
console.log(counterA());   // 2
console.log(counterB());   // 1 (NOT 3! — counterB has its own count)
console.log(counterA());   // 3
🔑 Rule: Each invocation of the factory function creates a completely new Execution Context with its own separate variables. The returned closures close over different memory locations. counterA and counterB do NOT share the same count.

⭐ 9. The Classic Interview Question — setTimeout + Loop

▼
⭐ THE most famous closure interview question in JavaScript. Master this.

The Bug:

for (var i = 1; i <= 3; i++) {
  setTimeout(function() {
    console.log(i);
  }, i * 1000);
}

// Output (after 1s, 2s, 3s):
// 4
// 4
// 4

Why 4, 4, 4?

  1. var i is function/global scoped — there is only ONE i in memory for all 3 iterations.
  2. The setTimeout callbacks are registered but don't execute immediately — they wait in the callback queue.
  3. By the time the loop finishes, i has been incremented to 4 (the value that fails the i <= 3 check).
  4. When the callbacks finally execute, they all look up the same reference to i → all see 4.
  5. Three setTimeout calls were made (i=1, 2, 3), so three outputs of 4.

Fix 1 — IIFE (Immediately Invoked Function Expression):

for (var i = 1; i <= 3; i++) {
  (function(j) {                    // IIFE creates a NEW scope each iteration
    setTimeout(function() {
      console.log(j);               // j is a SEPARATE variable per iteration
    }, j * 1000);
  })(i);                            // Pass current i as argument → becomes j
}

// Output: 1, 2, 3 ✅

Why it works: Each IIFE invocation creates a new Execution Context with its own parameter j. The setTimeout callback closes over j (not i). Each j is a different variable holding a different value (1, 2, 3).

Fix 2 — Just use let (The Modern Way):

for (let i = 1; i <= 3; i++) {
  setTimeout(function() {
    console.log(i);
  }, i * 1000);
}

// Output: 1, 2, 3 ✅

Why it works: let is block-scoped. The JS spec has special behavior for let in for loops: each iteration creates a completely new variable (new block scope, new binding). Each callback closes over its iteration's own i.

🎯 Interview Tip: Explain the bug first, then offer BOTH fixes. Show the IIFE to demonstrate closure understanding, then mention let as the modern solution. This shows depth AND practical knowledge.

10. Closures vs this — The Collision

▼
🧠 This is an advanced concept most developers get wrong.

The Rule:

  • Closures capture VARIABLES (like let count, const name) from the lexical environment.
  • Closures DO NOT capture the this keyword. Every regular function call generates a brand new this.
const user = {
  name: "Parth",
  greet: function() {
    const name = "Inner";     // a regular variable

    return function() {
      console.log(this.name); // this → determined by HOW this fn is called
      console.log(name);      // name → captured by closure from greet's scope
    };
  }
};

const fn = user.greet();
fn();   // Non-strict mode

// Output 1: ""        ← this = window, window.name = "" (browser quirk)
// Output 2: "Inner"   ← closure captured the variable 'name' from greet()

The Three Fixes for the "Lost this" Problem:

// Fix 1: The self trick (Pre-2015)
greet: function() {
  const self = this;           // Save this into a VARIABLE
  return function() {
    console.log(self.name);    // Closure captures 'self' ✅
  };
}

// Fix 2: Arrow function (Post-2015)
greet: function() {
  return () => {
    console.log(this.name);    // Arrow fn has no this → uses greet's this ✅
  };
}

// Fix 3: bind()
greet: function() {
  return function() {
    console.log(this.name);
  }.bind(this);                // Permanently bind this ✅
}
MechanismCaptured by Closure?How It's Resolved
Regular variables (let, const, var)✅ YESScope chain lookup (lexical)
this keyword❌ NODetermined at call-time (runtime binding)
arguments object❌ NO (in regular fn)Fresh one created per function call

11. Real-World Use Cases of Closures

▼

Use Case 1: Data Encapsulation / Privacy (Module Pattern)

function createBank() {
  let balance = 1000;    // Private! Cannot be accessed directly.

  return {
    deposit(amount)   { balance += amount; },
    withdraw(amount)  { balance -= amount; },
    getBalance()      { return balance; }
  };
}

const account = createBank();
account.deposit(500);
account.withdraw(200);
console.log(account.getBalance());   // 1300
console.log(account.balance);        // undefined — balance is PRIVATE!

The balance variable is completely inaccessible from outside. Only the returned methods (which form closures over balance) can read or modify it.

Use Case 2: Function Currying

function multiply(x) {
  return function(y) {
    return x * y;
  };
}

const double = multiply(2);    // x = 2 is "remembered"
const triple = multiply(3);    // x = 3 is "remembered"

console.log(double(5));   // 10
console.log(triple(5));   // 15

Use Case 3: Memoization (Caching)

function memoize(fn) {
  const cache = {};                    // Persists via closure

  return function(n) {
    if (cache[n] !== undefined) {
      console.log("From cache");
      return cache[n];
    }
    const result = fn(n);
    cache[n] = result;                 // Store in cache
    return result;
  };
}

const factorial = memoize(function(n) {
  return n <= 1 ? 1 : n * factorial(n - 1);
});

console.log(factorial(5));   // Computes: 120
console.log(factorial(5));   // From cache: 120

Use Case 4: once() — Run Only Once

function once(fn) {
  let called = false;
  let result;

  return function(...args) {
    if (!called) {
      called = true;
      result = fn(...args);
    }
    return result;
  };
}

const initialize = once(() => {
  console.log("Initialized!");
  return 42;
});

initialize();   // "Initialized!" → 42
initialize();   // (nothing logged) → 42 (cached result)
initialize();   // (nothing logged) → 42

12. Closures & Garbage Collection

▼

Normally, when a function finishes executing, its EC is deleted and variables are garbage collected. But closures prevent this for variables that are still referenced.

When IS the closed-over variable garbage collected?

function outer() {
  let secret = "hidden";
  return function() { console.log(secret); };
}

let fn = outer();    // secret persists — closure holds a reference
fn();                // "hidden"
fn = null;           // NOW secret can be garbage collected
                     // Because no closure references it anymore

Smart Engines Optimize — V8's Closure Pruning:

function heavy() {
  let bigArray = new Array(1000000).fill("data");   // 1 million items
  let smallVar = "hello";

  return function() {
    console.log(smallVar);    // Only references smallVar, NOT bigArray
  };
}

const fn = heavy();
EnginebigArray Garbage Collected?Why
V8 (Chrome/Node)✅ YESV8 analyzes the closure and prunes unreferenced variables
Older engines❌ Might persistSome engines keep the entire lexical environment

⚠️ setInterval Does NOT Overflow the Call Stack:

function setup() {
  let count = 0;

  setInterval(function() {
    count++;
    console.log(count);   // 1, 2, 3, 4... forever
  }, 1000);
}

setup();
Common misconception: "setInterval will overflow the call stack." WRONG.

Each callback runs, completes, and is popped off the stack before the next one arrives. They don't pile up. The stack never overflows.

But count is never garbage collected because the setInterval callback holds a closure over it forever. To release it, call clearInterval(intervalId).

13. Common Gotchas & Pitfalls

▼

Gotcha A: The setTimeout + var Loop (Most Famous Bug)

Covered in detail in Section 9. Remember: var creates ONE shared variable → all callbacks see the final value. Fix with IIFE or let.

Gotcha B: Closures Don't Capture this

Covered in Section 10. Regular functions get a fresh this every call. Use self trick, arrow functions, or .bind().

Gotcha C: Stale Closures in React (Preview)

// This is a common React bug — you'll encounter it in your React journey:
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);     // Always logs 0! Stale closure.
    }, 1000);
    return () => clearInterval(id);
  }, []);   // Empty dependency array = closure captures count = 0 forever
}

The setInterval callback closes over the initial count (0). Even as count changes via state updates, the closure still references the old value. This is called a "stale closure".

Gotcha D: Closures in a Loop Without Proper Scoping

var funcs = [];
for (var i = 0; i < 3; i++) {
  funcs.push(function() { console.log(i); });
}

funcs[0]();   // 3 (not 0!)
funcs[1]();   // 3 (not 1!)
funcs[2]();   // 3 (not 2!)

Same bug as setTimeout — all three functions close over the SAME var i, which is 3 when the loop ends.

15. Interview Answer Templates

▼

Q: "What is a Closure in JavaScript?"

"A closure is a function bundled together with its lexical scope. It allows an inner function to remember and access the variables of its outer function, even after the outer function has finished executing. Closures capture references to variables, not snapshots, meaning the inner function will see the updated value. They are formed at function definition time — not when the function is returned or called."

Q: "Do closures only work with return?"

"No. A closure is formed whenever a function is defined inside another scope and references that scope's variables. The function can be returned, passed as a callback to setTimeout, used as an event handler, or called directly. The return keyword doesn't create the closure — it just makes it visible to the outside world. The closure exists from the moment the function is born."

Q: "How is the scope chain different from a closure?"

"The scope chain is the mechanism — when a variable isn't found in the current scope, the engine walks up to the parent scope. A closure is what makes this mechanism work even after the parent function has finished executing. Normally, when a function's EC is destroyed, its variables are garbage collected. But if an inner function still references them, the closure preserves those variables so the scope chain still has something to walk up to. They're the same mechanism — closure just extends it beyond the parent's death."

Q: "Explain the setTimeout + loop problem and how to fix it."

"When you use var in a for loop with setTimeout, all callbacks share the same variable reference. By the time the callbacks fire, the loop has finished and the variable holds the final value. You can fix it two ways: using an IIFE to create a new scope per iteration, capturing the current value as a parameter, or simply using let which creates a new block-scoped binding per iteration."

17. Answer Key

▼

Q1

"Hello"

NOT a closure. sayHi is defined inside greet (condition 1 ✅), but it only uses its OWN variable greeting — it never references name from greet (condition 2 ❌). No closure formed.

← Back to Question 1

Q2

10

outer() is still alive on the Call Stack when inner() runs. This is just normal scope chain lookup — the engine walks up and finds x = 10 in the living parent. The closure reference exists but the parent is alive — nothing special needed.

← Back to Question 2

Q3

10

outer() is dead when fn() runs — its EC was destroyed after returning. x comes from the closure — the preserved [[Scope]] reference that inner carries. This is the "scope chain surviving death" in action.

← Back to Question 3

Q4

1 (at 1s), 2 (at 2s), 3 (at 3s)... forever

setup() finishes instantly. count survives via closure. Each callback runs, increments, logs, and completes before the next one fires. No stack overflow. To stop and allow GC: clearInterval().

← Back to Question 4

Q5

"initial"
"updated"
"final"

Both writer and reader close over the same secret variable (same closure, same reference). writer modifies it, reader reads the updated value.

← Back to Question 5

Q6

100

test() is dead when the callback fires after 2 seconds. The callback accesses a through its closure. Closures capture references, not snapshots. a was updated to 100 synchronously before test() even finished. The callback sees 100.

← Back to Question 6

Q7

A: undefined
B: 99

this.value: naked call → this = window → window.value doesn't exist → undefined. value (without this): closure captures the local variable value = 99 from createFn's scope. Closures capture variables, NOT this.

← Back to Question 7

Q8

"Clicked 1 times"
"Clicked 2 times"
"Clicked 3 times"

clickCount is NOT dead — the event handler callback holds a closure over it. Outer scope: attachHandler. Inner fn: anonymous click handler. Variable closed over: clickCount.

← Back to Question 8

Q9

Timer: 1     ← fn() call 1 (immediate)
Timer: 2     ← fn() call 2 (immediate)
Timer: 3     ← setTimeout #1 (after 1s)
Timer: 4     ← setTimeout #2 (after 2s)

All 3 functions (returned fn + 2 setTimeout callbacks) close over the same count and name. They share one variable and increment it sequentially.

← Back to Question 9

Q10

24
100

createMultiplier(2) → remembers x = 2. step1(3) → remembers x = 2 AND y = 3. step2(4) → 2 × 3 × 4 = 24. createMultiplier(5)(10)(2) → 5 × 10 × 2 = 100. Each nested function forms a closure over all parent variables in its chain.

← Back to Question 10

🔹 Two conditions: defined inside + references outer variable

🔹 Formed at birth. Delivery method (return/callback/setTimeout) is irrelevant.

🔹 Closure = Scope Chain that survives parent's death

🔹 Captures REFERENCES, not snapshots. Captures variables, NOT this.
