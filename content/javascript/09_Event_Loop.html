Chapter 7 — The JavaScript Codex | Week 2

How single-threaded JavaScript does async work without blocking — the #1 frontend interview topic.

🔗 Companion file: JS Engine & V8 Architecture (what's inside the engine that runs all this)

1. The Problem the Event Loop Solves

▼
The core paradox: JavaScript is synchronous and single-threaded — one call stack, one thing at a time, top to bottom. Yet it can wait 5 seconds for a timer, fetch from a server, and respond to clicks — without freezing the page. How? That's what the Event Loop explains.

If JavaScript were only the call stack, then "wait 5 seconds" would block everything — the whole page frozen until done. Unusable.

The trick: JavaScript itself doesn't handle timers, network calls, or the DOM. The browser does. JavaScript hands slow jobs to the browser, keeps running the rest of the code, and the browser hands results back later through a queue system managed by the Event Loop.

🔑 One-line summary: The Event Loop lets single-threaded JavaScript delegate slow work to the browser and pick up results later — without ever blocking the main thread.

2. The Browser's Superpowers (Web APIs)

▼

The JS Engine (like V8) is small — just the Call Stack + Memory Heap. On its own it cannot set a timer, make a network call, or touch the page. The browser wraps the engine and gives it superpowers via Web APIs — NOT part of JavaScript:

Superpower (Web API)What it does
setTimeout / setIntervalTimers
fetch / XMLHttpRequestNetwork calls to servers
DOM APIs (document.*)Access & modify the page
consoleLogging
localStoragePersistent storage
Event listeners (addEventListener)Respond to clicks, scrolls, etc.
💡 How JS accesses them: All superpowers are exposed through the global window object. setTimeout(...) is really window.setTimeout(...). Same for console.log, fetch, etc. window is the bridge between your JS code and the browser's superpowers. (The very next section explains the exact memory-level mechanism behind this.)
🔑 Key takeaway: setTimeout, fetch, and the DOM are browser features, not JavaScript features. Node.js provides its own versions. This is why the same JS behaves differently in a browser vs Node.

⭐ 3. How Naked Global Calls Resolve (setTimeout, fetch, console)

▼
⭐ The question most people never ask: If these APIs live on window, why can we call setTimeout(...) directly instead of window.setTimeout(...)? How does the naked call actually resolve at the memory level?

The Short Answer

When you write setTimeout(...), the engine performs an identifier lookup through the scope chain — the same lookup as for any variable. It's not in your local scope, so it walks up... and up... until it reaches the Global Scope. And here's the key: at the global level, the scope's storage IS the global object (window). So setTimeout and window.setTimeout resolve to the exact same function.

💡 window. is just the explicit path. The naked call is the engine walking the scope chain and arriving at the same destination on its own.

The Machinery — The Global Environment Has TWO Records

You know from the Execution Context notes that every scope has a Lexical Environment. But the global lexical environment is special — the spec splits it into two separate storage records:

Who Put These On window? (The Browser Did)

The JS engine (V8) has no idea what setTimeout or fetch is — it's just Call Stack + Heap. When the browser builds the Runtime Environment (before your code runs), it pre-loads window with all the Web APIs. Conceptually:

// The browser does this BEFORE your code runs:
window.setTimeout   = function(cb, delay) { /* timer machinery */ };
window.fetch        = function(url) { /* network machinery */ };
window.console      = { log: function() { /* logging */ }, ... };
window.localStorage = { /* storage machinery */ };
// ...every Web API, installed as a property of window

So by the time your code runs, window is pre-filled. Your naked calls resolve into it via the scope chain. In Node.js, the global object is globalThis/global, pre-filled with different superpowers (file system, etc.) — which is why there's no document in Node.

The Callback to Your Hoisting Notes — var vs let at Global Level

This is exactly why window.b was undefined for a global let:

var a = 10;
let b = 20;
function c() {}

console.log(window.a);   // 10          ✅ var → Object Record (on window)
console.log(window.b);   // undefined   ❌ let → Declarative Record (NOT on window)
console.log(window.c);   // function c  ✅ function decl → Object Record (on window)
DeclarationGoes intoOn window?Reachable by naked name?
varObject Env Record✅ Yes✅ Yes (scope chain)
function declarationObject Env Record✅ Yes✅ Yes
let / const / classDeclarative Env Record ("Script" scope)❌ No✅ Yes (scope chain)
💡 Notice: BOTH records are part of the global scope, so BOTH are reachable by naked name via the scope chain. The only difference is whether they're ALSO exposed as a property on window. var/functions are; let/const/class are not.
🎯 The one-line mental model: The global scope and the global object aren't two loosely-linked things — the global object (window) is the physical backing store for the Object Environment Record half of the global scope. That's why looking up a naked global identifier and reading a property off window are the same operation, and why no window. prefix is needed.

5. How It Works — A Full Trace

▼
console.log("Start");
setTimeout(() => { console.log("Timeout"); }, 2000);
console.log("End");
1. "Start" pushed to Call Stack → logged → popped.
2. setTimeout(cb, 2000) hits the stack.
   → JS hands cb + 2000ms timer to the Web APIs.
   → Browser starts a 2-second timer OFF the main thread.
   → setTimeout returns immediately. JS does NOT wait.
3. "End" pushed → logged → popped.
4. Call Stack now EMPTY. Main script done.
   (Browser's timer still counting...)
5. After 2s, timer expires → browser puts cb into CALLBACK QUEUE.
6. Event Loop: "Is Call Stack empty?" → YES → moves cb onto stack.
7. cb runs → "Timeout" logged → popped.

Output:

Start
End
Timeout   ← after 2 seconds, even though written in the middle
💡 This is why setTimeout is non-blocking. The 2-second wait happens in the browser, not on the call stack. JS keeps running "End" immediately.
⚠️ setTimeout(fn, 0) is NOT instant. Even with 0ms, the callback still goes through Web API → Callback Queue → Event Loop. It runs only after current sync code finishes AND the stack is empty AND all microtasks are done.

⭐ 6. Microtask Queue vs Callback (Macrotask) Queue

▼
⭐ THE distinction interviewers test. Two waiting queues, one has priority.
Microtask QueueCallback / Macrotask Queue
PriorityHIGH — drained firstLOW — only when microtasks empty
Holds callbacks fromPromises (.then/.catch/.finally), async/await, queueMicrotasksetTimeout, setInterval, DOM events, I/O
Also calledJob QueueTask Queue, Macrotask Queue

The Classic Proof:

console.log("1");
setTimeout(() => console.log("2"), 0);          // → Callback Queue
Promise.resolve().then(() => console.log("3")); // → Microtask Queue
console.log("4");
Sync phase:       "1", "4" logged.            → 1, 4
Stack empty. Event Loop runs.
Microtasks FIRST: "3" logged.                 → 3
Then macrotasks:  "2" logged.                 → 2
Output: 1, 4, 3, 2
🔑 The mental model: Sync code first. THEN microtask queue drains completely. THEN one macrotask. Then microtasks drain again. Then next macrotask. And so on.

7. The Golden Rule (Exact Priority Order)

▼
Memorize this exact cycle. It answers EVERY event-loop question:
  1. Run all synchronous code (top to bottom) until the call stack is empty.
  2. Drain the ENTIRE microtask queue — including microtasks added while draining — until completely empty.
  3. Run exactly ONE macrotask from the callback queue.
  4. Go back to step 2 — drain all microtasks again.
  5. Repeat: one macrotask → drain all microtasks → one macrotask → ...
SYNC CODE  →  [ALL microtasks]  →  1 macrotask  →  [ALL microtasks]  →  1 macrotask  →  ...
⚠️ The crucial part people miss: Microtasks drain completely before each macrotask. If a microtask adds another microtask, that new one ALSO runs before any macrotask.
🎯 Interview technique: Keep 3 lists on paper — (1) sync output, (2) microtask queue, (3) macrotask queue in registration order. Listing macrotasks in registration order is where the "wrote F instead of E" type slip happens.

⚠️ 9. The fetch Trap — Promises Aren't Instant

▼
The subtle trap: "Microtasks beat macrotasks" is only true when both are ready at the same moment. A real fetch is NOT ready instantly — it waits on the network.
console.log("Parth");
fetch("https://api.example.com/data").then(() => console.log("API RESPONSE"));
setTimeout(() => console.log("Timer Done"), 0);
console.log("Gupta");

Tempting (WRONG) answer: Parth, Gupta, API RESPONSE, Timer Done

Actual real-world output: Parth, Gupta, Timer Done, API RESPONSE

1. "Parth", "Gupta" — sync, logged immediately.
2. fetch(...) starts a NETWORK CALL — takes REAL time (50ms, 200ms...).
   Its .then goes to the microtask queue ONLY AFTER the response arrives.
3. setTimeout(0) timer expires almost immediately → macrotask queue.
4. Stack empty. Microtask queue EMPTY (fetch hasn't responded yet!).
   → Event loop runs the macrotask: "Timer Done".
5. Later, network responds. fetch's .then runs: "API RESPONSE".
⚠️ The lesson: The microtask-beats-macrotask rule assumes both are ready at the same instant. To cleanly demonstrate microtask priority, use Promise.resolve().then(...) — that resolves immediately.

⚠️ 10. Returned Promise = Extra Microtask Ticks

▼
Advanced but interview-relevant. When a .then() callback returns a Promise, the chain needs extra microtask "ticks" to unwrap it before the next .then() runs.
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => {
  console.log("C");
  return Promise.resolve();     // ← returns a Promise!
}).then(() => console.log("D"));
setTimeout(() => console.log("E"), 0);
Promise.resolve().then(() => console.log("F"));
console.log("G");

Output: A, G, C, F, D, B, E

SYNC:  "A", "G".  Macrotasks: [B, E]  Microtasks: [C-cb, F-cb]
DRAIN MICROTASKS:
  C-cb → "C". Returns a promise → next .then(D) needs extra ticks.
  F-cb → "F".
  (extra ticks resolve) → .then(D) scheduled → "D".
  Microtask queue empty. (D still beat the macrotasks!)
MACROTASKS (registration order): "B", then "E".
Output: A, G, C, F, D, B, E
💡 Key insight: Even with extra ticks, D runs before B/E because the ENTIRE microtask queue (including new microtasks) empties before any macrotask. And macrotask order is registration order: B before E.

11. Starvation of the Callback Queue

▼

Because microtasks always drain completely before any macrotask, macrotasks can theoretically never run if microtasks keep adding more microtasks endlessly.

function loop() {
  Promise.resolve().then(loop);   // each microtask schedules another
}
loop();
setTimeout(() => console.log("I will NEVER run"), 0);
// Macrotask starves forever — microtasks never stop.
⚠️ "Starvation." The setTimeout is stuck forever because the microtask queue never empties. Explains WHY heavy Promise chains can delay timers and rendering.

12. Common Gotchas

▼

Gotcha A: setTimeout(fn, 0) ≠ "right now"

console.log("1");
setTimeout(() => console.log("2"), 0);
console.log("3");
// Output: 1, 3, 2

Gotcha B: Timer delay is a MINIMUM, not a guarantee

setTimeout(() => console.log("done"), 100);
// If the call stack is busy for 5 seconds, this won't run at 100ms.
// "100ms" = "at least 100ms."

Gotcha C: A long synchronous task freezes everything

setTimeout(() => console.log("timer"), 10);
const end = Date.now() + 5000;
while (Date.now() < end) { }   // stack busy — nothing else runs
console.log("sync done");
// Output: "sync done" THEN "timer" — timer expired long ago but couldn't run.

Gotcha D: async/await is microtasks in disguise

async function foo() {
  console.log("1");
  await null;              // everything AFTER await = microtask
  console.log("2");
}
console.log("A");
foo();
console.log("B");
// Output: A, 1, B, 2

Gotcha E: Sync code always finishes before any microtask

Promise.resolve().then(() => console.log("micro"));
console.log("sync");
// Output: sync, micro

14. Interview Answer Templates

▼

Q: "Explain the event loop."

"JavaScript is single-threaded with one call stack, so it does one thing at a time. Slow operations like timers, network calls, and DOM events are handled by the browser's Web APIs, off the main thread. When they finish, their callbacks go into a queue. The event loop continuously checks whether the call stack is empty, and if so, moves waiting callbacks onto the stack. That's how single-threaded JS handles async work without blocking."

Q: "Why can we call setTimeout without window.?"

"When you write a naked setTimeout, the engine resolves it as an identifier by walking up the scope chain until it reaches the global scope. At the global level, the scope's Object Environment Record is backed by the window object itself — so looking up setTimeout in the global scope is the same as reading window.setTimeout. The browser pre-installs all Web APIs as properties of window before your code runs. So setTimeout and window.setTimeout are literally the same function reference."

Q: "Microtask vs macrotask queue?"

"The microtask queue holds Promise callbacks — then/catch/finally and code after await. The macrotask queue holds setTimeout, setInterval, and DOM events. Microtasks have higher priority: after each sync run, the event loop drains the ENTIRE microtask queue before running a single macrotask, then repeats."

Q: "Does setTimeout(fn, 0) run immediately?"

"No. Even with 0ms, the callback goes through the Web API, then the callback queue, then waits for the event loop. It runs only after all sync code finishes, the stack is empty, and the microtask queue is fully drained."
