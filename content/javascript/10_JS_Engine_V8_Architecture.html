1. The JavaScript Runtime Environment

▼
Big idea: "JavaScript runs everywhere" — browsers, servers, smart watches, robots, IoT devices, even lightbulbs. That's only possible because each of those places provides a JavaScript Runtime Environment (JRE). The JRE is the big container that has everything needed to run JS code. Without it, JS cannot run.

What's inside a Runtime Environment?

ComponentRole
JS EngineThe "heart" — actually runs the code (e.g. V8)
Web APIs / APIsSuperpowers connecting to the outer world: timers, fetch, DOM, localStorage, or custom hardware APIs
Event LoopCoordinates async callbacks (see companion notes)
Callback & Microtask QueuesWhere waiting callbacks sit
💡 Custom device example: To run JS on a smart water cooler, you just install a JRE on it and provide the necessary APIs — e.g. a getWaterLevel() API. The engine runs the JS; the environment provides the device-specific superpowers.
🔑 The key insight: The JS Engine alone can't do much — it can only run pure JavaScript logic. It's the surrounding Runtime Environment that gives it superpowers (like setTimeout or fetch). Different environments provide different superpowers. That's why JS behaves differently in a browser vs Node.js.

2. Browser vs Node.js vs Other Environments

▼

The most famous JRE is the browser. Every browser has a JS engine inside it. But it's not the only one.

EnvironmentWhat makes it special
BrowserHas a JS engine + Web APIs (DOM, fetch, localStorage, timers). Runs JS on the client.
Node.jsAn open-source C++ program that provides a JRE outside the browser (on servers). Uses Google's V8 engine, but provides different superpowers (file system, HTTP server modules) instead of the DOM.
OthersSmart watches, IoT devices, embedded systems — each with a JRE tailored to its capabilities.
💡 Concrete example: setTimeout exists in BOTH the browser and Node.js — and looks identical in your code. But internally they're implemented differently. The browser's version and Node's version are separate pieces of machinery that happen to share the same name and behavior. This is why "JS is JS everywhere" but the surrounding APIs differ.
⚠️ Interview clarity: Node.js is not a language and not an engine. It's a runtime environment that embeds the V8 engine and adds server-side superpowers. People often confuse this.

3. What IS a JavaScript Engine? (Demystified)

▼
Clearing up the biggest misconception: A JS Engine is NOT a machine. It's not some magical hardware. It's just a program — software written in a low-level language (V8 is written in C++). Its job is to take human-readable JS code and convert it into machine-level code that runs.

People new to the field imagine the "engine" as something exotic. In reality, it's a normal application, like any other program, whose job is to take your JavaScript code and run it.

🔑 Mental model: The engine takes your code as text input, processes it through several internal steps, and produces running behavior as output. Just like a compiler or interpreter for any other language.

4. ECMAScript & The Different Engines

▼

ECMAScript is the governing standard (the official specification) for JavaScript. It's the rulebook that says how the language must behave. Anyone can build a JS engine — as long as it follows the ECMAScript rules.

💡 The precise detail: "JavaScript" is actually a trademarked name. The core language is standardized by an organization called ECMA International. The specification document is called ECMA-262, and the language it defines is ECMAScript. When you hear "ES6" or "ES2015" (which brought let/const, arrow functions, etc.), that's just an update to the ECMAScript standard. V8, SpiderMonkey, and Chakra are all different companies building engines that follow the exact same ECMA-262 rulebook.

Because of this open standard, there are many different engines, each built by different companies:

EngineBuilt byUsed in
V8GoogleChrome, Edge, Node.js, Deno
SpiderMonkeyMozilla — the FIRST ever JS engine, created by Brendan Eich (JS's creator) at NetscapeFirefox
JavaScriptCoreAppleSafari
ChakraMicrosoftold Edge (legacy)
🔑 Why this matters: Every engine must follow ECMAScript, so your JS behaves consistently across browsers. But each engine is free to implement the internals differently — different optimization strategies, different speeds. This is why the same code can run at different speeds in Chrome vs Firefox.

6. Step 1 — Parsing (Tokens & the AST)

▼

Parsing is the first thing the engine does. It has two sub-parts:

Sub-step A — Tokenization (the Tokenizer / Lexer)

The engine breaks your code into small meaningful pieces called tokens. For example:

let a = 7;

...is broken into these tokens:

[ "let" ]  [ "a" ]  [ "=" ]  [ "7" ]  [ ";" ]
   keyword   identifier  operator  value  semicolon

Sub-step B — Building the AST (Syntax Parser)

The tokens are fed into a syntax parser, which converts them into an AST — Abstract Syntax Tree: a tree-structured object (like JSON) representing the structure of your code.

let a = 7;

becomes (simplified AST):

VariableDeclaration
├── kind: "let"
└── Declaration
    ├── Identifier: "a"
    └── Literal (value): 7
💡 See it yourself: Visit astexplorer.net, paste any JS code, and watch it turn into an AST in real time.
🔑 Why an AST — and where you already use it: A tree is far easier to analyze and transform than raw text. This is exactly how your everyday tools work under the hood:
  • Babel — converts modern JS → older JS by analyzing & rewriting the AST
  • ESLint — checks your code for errors by inspecting the AST
  • Prettier — reformats your code by parsing it to an AST and re-printing it
So the AST isn't just engine trivia — it powers the tooling you'll use every day.

7. Interpreter vs Compiler — Is JS Interpreted or Compiled?

▼
⭐ Classic interview question: "Is JavaScript an interpreted or a compiled language?" The honest answer: both (in modern engines). Here's why.
InterpreterCompiler
How it worksReads & executes code line-by-line, immediatelyTranslates the whole code to optimized machine code first, then runs it
Startup speedFAST — starts running right awaySLOWER to start (must compile first)
Runtime speedSlower (no deep optimization)FAST — optimized code runs quickly
AnalogyTranslating a speech live, sentence by sentenceTranslating a whole book, then handing over the polished version

JavaScript was originally designed as an interpreted language — so it could start quickly in browsers. But interpreters are slow for heavy, repeated code.

🔑 The modern answer: Today, almost all modern JS engines use BOTH an interpreter AND a compiler together. This combination is called JIT (Just-In-Time) Compilation. So modern JavaScript is best described as a Just-In-Time compiled language — it gets the fast startup of an interpreter AND the runtime speed of a compiler.

⭐ 8. Step 2 — JIT (Just-In-Time) Compilation

▼
⭐ This is what makes modern JavaScript fast. JIT = an interpreter for fast startup + a compiler for runtime speed, working together.
            AST
             │
             ▼
    ┌──────────────────┐
    │   INTERPRETER    │  converts AST → bytecode and executes
    │  (fast startup)  │  IMMEDIATELY, line by line
    └────────┬─────────┘
             │  while running, watches for "hot" code
             │  (code that runs many times, like loops)
             ▼
    ┌──────────────────┐
    │    COMPILER      │  takes hot code and OPTIMIZES it into
    │  (runtime speed) │  highly efficient machine code
    └──────────────────┘
             │
             ▼
   Optimized code replaces the slow version → runs super fast

The step-by-step story:

  1. The interpreter takes the AST and starts producing bytecode, executing it immediately — so the program starts fast, no waiting.
  2. While running, the engine monitors which code runs frequently ("hot" code — e.g. a loop running a million times).
  3. The compiler kicks in concurrently and optimizes that hot code into fast machine code, replacing the slower bytecode.
  4. This isn't one-time — the compiler can optimize (and even de-optimize if assumptions break) multiple times as the program runs.
💡 Why "Just-In-Time"? Because compilation happens during execution (just in time to run), not entirely beforehand like a traditional compiled language (e.g. C++). The engine compiles code right as it's needed.
🔑 The payoff: Fast startup (from the interpreter) + fast repeated execution (from the compiler optimizing hot code). Engines like V8 pour enormous engineering effort into these optimization algorithms — squeezing out microseconds.

10. Garbage Collection (Mark & Sweep)

▼

The engine runs a Garbage Collector — a program that automatically frees up heap memory that's no longer being used, so your app doesn't run out of RAM. Memory leaks crash applications; the GC prevents that.

The famous algorithm: Mark & Sweep (two phases)

PHASE 1 — MARK:
  Start at the "root" (in browsers, the `window` object).
  Travel through every variable/object reachable from the root.
  Mark each one as "reachable" / "active".

PHASE 2 — SWEEP:
  Scan the entire Memory Heap.
  Anything NOT marked in Phase 1 is "unreachable" — your program
  can no longer access it. Sweep it away and free that RAM.
💡 Connecting to closures (Ch 2): Remember how closures keep variables alive? That's the garbage collector choosing not to sweep them because the closure still references them (they're still "reachable" from the root). When you set the closure to null, the reference breaks, the variable becomes unreachable, and Mark & Sweep finally collects it.
🔑 Key point: JavaScript is automatically garbage collected — unlike C/C++ where you manually free memory. "Mark & Sweep" is a very common interview keyword.

11. Why Browsers Compete on JS Speed

▼

Every browser wants its JavaScript engine to be the fastest. This competition is why the web keeps getting faster.

  • Google's V8 pioneered aggressive JIT optimization → Chrome felt lightning fast → set the bar.
  • Every engine team pours effort into better optimization algorithms — shaving off microseconds.
  • Because they all follow ECMAScript, your code behaves the same everywhere — but the internal machinery races to be quickest.
💡 Takeaway: The reason modern JavaScript can power heavy apps (Google Docs, Figma, VS Code) is decades of engine optimization — parsing improvements, smarter JIT compilers, and efficient garbage collectors, all competing to win.

⚡ 11a. V8 Optimization Techniques BONUS / ADVANCED

▼
🎁 Honesty note: This section is advanced. It occasionally comes up at senior / product-company interviews and shows genuine depth — but you will NOT be rejected for not knowing it. Skim it, understand the gist, don't grind on it. Prioritize the core sections above for interviews.

These are specific tricks the optimizing compiler uses to make hot code faster. All three are worth understanding at a "one-sentence" level.

1. Inlining

Calling a function has overhead — pushing to the call stack, creating an execution context, popping it off. For a tiny function called constantly, that overhead adds up.

function add(a, b) { return a + b; }
let sum = add(5, 5);

// The compiler INLINES it — replaces the call directly with the body:
let sum = 5 + 5;   // function call bypassed entirely

In one line: the compiler replaces a small function call with the function's actual code, skipping the call overhead.

2. Copy Elision

When passing objects around, computers often copy the object from one memory location to another — wasting RAM and CPU.

In one line: the compiler realizes an unnecessary copy can be skipped — it lets the new variable point to the original memory instead of duplicating it. It "elides" (omits) the copy.

3. Inline Caching

JavaScript is dynamically typed, so the engine normally has to search an object's internal "dictionary" to find where a property lives — every single time.

const user = { name: "Parth" };
// Reading user.name repeatedly (e.g. in a loop):
for (...) { console.log(user.name); }

// Normally: search the object's memory dictionary each time.
// With Inline Caching: remember the exact memory offset of `name`
// after the first lookup, then grab it directly next time.

In one line: the engine caches where a property lives so repeated lookups skip the search.

🔑 The theme: All three optimizations remove repeated, redundant work in hot code — bypassing call overhead (inlining), skipping needless copies (copy elision), and remembering property locations (inline caching). This is the kind of thing V8's compiler does "day and night" to win the speed race.

Google gave cool codenames to the internal parts of the V8 engine:

13. Interview Answer Templates

▼

Q: "What is a JavaScript engine?"

"A JavaScript engine is a program — not a machine — that takes your JavaScript code as input and executes it. The most famous is Google's V8, written in C++, which powers Chrome and Node.js. It works in three broad steps: parsing the code into an Abstract Syntax Tree, compiling that using Just-In-Time compilation, and executing it using the call stack and memory heap."

Q: "Is JavaScript interpreted or compiled?"

"Historically it was interpreted, for fast startup in browsers. But modern engines use both an interpreter and a compiler together, called Just-In-Time (JIT) compilation. The interpreter starts executing immediately for fast startup, while the compiler optimizes frequently-run 'hot' code into fast machine code during execution. So modern JavaScript is best described as a JIT-compiled language."

Q: "What is an AST?"

"An Abstract Syntax Tree is a tree-structured representation of your code that the engine builds during parsing. First a tokenizer breaks the code into tokens, then a syntax parser assembles those into the AST. It's not just engine internals — tools like Babel, ESLint, and Prettier all work by analyzing and transforming the AST."

Q: "How does JavaScript manage memory?"

"JavaScript is automatically garbage collected — unlike C++ where you free memory manually. The garbage collector uses the Mark and Sweep algorithm: starting from the root, it marks all reachable objects, then sweeps away and frees everything unmarked. This is also why closures keep variables alive — the GC won't sweep something the closure still references."

Q (senior): "How does V8 make JavaScript fast?"

"V8 uses JIT compilation — an interpreter called Ignition for fast startup, and an optimizing compiler called TurboFan that optimizes hot code at runtime using techniques like inlining, copy elision, and inline caching. Its garbage collector, Orinoco, runs concurrently on background threads so memory cleanup doesn't freeze the UI — avoiding the old 'stop the world' problem."

The engine alone runs pure JS; the runtime gives it timers, fetch, DOM access, etc.

Q5 — Answer

Q6 — Answer

The interpreter takes the AST and executes immediately (fast startup). While running, the engine monitors which code runs frequently — "hot" code (e.g. a loop running a million times). The compiler then optimizes that hot code into efficient machine code, replacing the slower version. It can happen multiple times, and de-optimize if assumptions break. Result: fast startup AND fast repeated execution.

← Back to Question 6

Q7 — Answer

JavaScript is automatically garbage collected — no manual freeing like C/C++. Algorithm: Mark & Sweep. Phase 1 (Mark): starting from the root (the window object in browsers), mark every reachable/referenced object as active. Phase 2 (Sweep): scan the heap and free everything not marked (unreachable). Closure connection: a closure keeps variables alive because they remain reachable/referenced by the inner function, so the GC won't sweep them. Set the closure to null → reference breaks → unreachable → collected.

← Back to Question 7

Q8 — Answer

V8's interpreter is Ignition; its optimizing compiler is TurboFan. Optimization techniques: Inlining (replace a small function call with its body), Copy Elision (skip unnecessary object copies), Inline Caching (remember a property's memory location to skip repeated lookups). Concurrent GC (Orinoco) solved the "stop the world" problem — older GCs froze the whole page during cleanup; Orinoco runs cleanup on background threads so the UI doesn't freeze.
