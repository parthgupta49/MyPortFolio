1. What is a Prototype?

▼
Core Idea: When you create a JavaScript object, array, or function, the JS engine automatically attaches a hidden object to it. That hidden object is called the Prototype. It contains built-in helper methods and properties.

This is why you can call methods on things you never defined them on. The methods live on the prototype, and your object inherits access to them.

Proof — Arrays Have Methods You Never Defined:

const arr = ["Parth", "Deepika"];

// You never wrote push, pop, map, filter, etc.
// But they all work:
arr.push("Aditya");     // ✅ works
arr.map(x => x);        // ✅ works
arr.filter(x => x);     // ✅ works

// Where are these methods coming from?
console.log(arr.__proto__);  // Array.prototype — contains all array methods

Proof — Objects Have Methods You Never Defined:

const obj = { name: "Parth" };

// You never wrote toString or hasOwnProperty.
// But they work:
obj.toString();                    // "[object Object]"
obj.hasOwnProperty("name");        // true

// Where are these methods coming from?
console.log(obj.__proto__);        // Object.prototype

Proof — Functions Have Methods You Never Defined:

function fn() { }

// You never wrote call, apply, or bind.
// But they work:
fn.call();
fn.apply();
fn.bind();

// Where are these methods coming from?
console.log(fn.__proto__);         // Function.prototype

The Hidden Attachment — Visualized:

const arr = ["Parth"];

MEMORY:
┌────────────────────┐
│  arr               │
│  ├── [0]: "Parth"  │
│  ├── length: 1     │
│  └── __proto__ ─────┐    ← hidden reference the engine adds
└─────────────────────┼───→ Array.prototype
                      │      ├── push
                      │      ├── pop
                      │      ├── map
                      │      ├── filter
                      │      └── ...
🔑 Key Insight: Prototypal inheritance in JavaScript is not classical inheritance like Java or C++. Forget classes and parent/child hierarchies for a moment. In JS, inheritance is simply "one object accessing the methods and properties of another object" through a hidden link (__proto__).

⚡ 2. __proto__ vs prototype — The Sharp Distinction

▼
🧠 This is THE most confusing pair in JavaScript. They sound similar, are related, but do completely different things. Get this section right and 80% of prototype confusion disappears.

The One-Line Difference:

PropertyWho Has It?What Is It?
SomeFunction.prototype ONLY functions (constructor functions) A container object where you attach methods that instances will inherit
someObject.__proto__ Every object / instance A reference (pointer) to its prototype — the object it inherits from

Full Visualization:

function Person(name) {
  this.name = name;
}
Person.prototype.greet = function() { return "Hi"; };

const p = new Person("Parth");
FUNCTION SIDE                      INSTANCE SIDE
─────────────                      ─────────────

Person (the function)              p (the instance)
├── name: "Person"                 ├── name: "Parth"
├── length: 1                      │
├── prototype ──────┐              ├── __proto__ ─┐
│                   │              │              │
└── (function code) │              └── (data)     │
                    ↓                             │
             ┌────────────────┐ ←─────────────────┘
             │ Person.prototype│
             │ (an object)     │
             │ ├── greet: fn   │
             │ ├── constructor │
             │ └── __proto__ ──┐
             └─────────────────┼──→ Object.prototype
                               │      ├── toString
                               │      ├── hasOwnProperty
                               │      └── __proto__ ──→ null

The Connection Between Them:

p.__proto__ === Person.prototype;   // true ✅

// When you do `new Person(...)`, the engine sets the new instance's
// __proto__ to point to Person.prototype. THAT is the link that makes
// inheritance work.
🎯 The Memory Aid:
• prototype lives on the function/class — it's the template (what will be inherited).
• __proto__ lives on the instance — it's the link (pointing to that template).

Why the Weird __proto__ Name?

The double underscores (called "dunder" — double underscore) are a signal to developers: "this is internal, don't accidentally mess with it." It's visually distinct so you never type it by mistake.

Modern Best Practice:

// __proto__ is technically deprecated (though universally supported)
// Modern equivalents:

Object.getPrototypeOf(p);              // read prototype (replaces p.__proto__)
Object.setPrototypeOf(p, newProto);    // write prototype (replaces p.__proto__ = ...)

// For learning and debugging in DevTools, __proto__ is still fine.
// For production code, use the Object methods.

3. The Prototype Chain

▼

Because every prototype is itself an object, it has its own prototype. Follow the __proto__ pointers, and you get a chain. This is the Prototype Chain.

The Array Prototype Chain:

const arr = [1, 2, 3];

arr.__proto__                              → Array.prototype
arr.__proto__.__proto__                    → Object.prototype
arr.__proto__.__proto__.__proto__          → null

VISUALIZED:
┌──────┐   ┌─────────────────┐   ┌──────────────────┐   ┌──────┐
│ arr  │──→│ Array.prototype │──→│ Object.prototype │──→│ null │
└──────┘   └─────────────────┘   └──────────────────┘   └──────┘
           (push, map, filter,   (toString, hasOwn,      (end of chain)
            forEach, ...)         valueOf, ...)

The Object Prototype Chain:

const obj = { name: "Parth" };

obj.__proto__                              → Object.prototype
obj.__proto__.__proto__                    → null

┌──────┐   ┌──────────────────┐   ┌──────┐
│ obj  │──→│ Object.prototype │──→│ null │
└──────┘   └──────────────────┘   └──────┘

The Function Prototype Chain:

function fn() {}

fn.__proto__                               → Function.prototype
fn.__proto__.__proto__                     → Object.prototype
fn.__proto__.__proto__.__proto__           → null

┌──────┐   ┌───────────────────┐   ┌──────────────────┐   ┌──────┐
│ fn   │──→│ Function.prototype│──→│ Object.prototype │──→│ null │
└──────┘   └───────────────────┘   └──────────────────┘   └──────┘
           (call, apply, bind)     (toString, hasOwn)     (end)
🔑 The Universal Truth: "Everything in JavaScript is an object." Arrays, functions, and custom objects — all eventually reach Object.prototype, and then null. This is why you can call .toString() on literally anything.

The End of the Chain — null:

Object.prototype.__proto__ === null

Every chain terminates at null. When the engine reaches null while searching for a property, it stops looking and returns undefined.

4. Property Lookup Algorithm

▼

When you access a property or method (like obj.someMethod()), here's exactly what the engine does:

The Algorithm:

function lookup(obj, propertyName) {
  let current = obj;

  while (current !== null) {
    if (current has propertyName as OWN property) {
      return current[propertyName];   // ✅ Found it! Stop.
    }
    current = current.__proto__;      // Move up the chain
  }

  return undefined;                    // ❌ Reached null. Not found.
}

Example — Trace Through:

const parent = { greet: function() { return "Hello"; } };
const child = Object.create(parent);
child.name = "Parth";

child.name;         // How does the engine find this?
child.greet();      // How does the engine find this?
child.toString();   // How does the engine find this?

Lookup for child.name:

Step 1: Look in child's own properties → { name: "Parth" }
         Found "name"! → return "Parth"  ✅

Lookup for child.greet:

Step 1: Look in child's own properties → { name: "Parth" }
         Not found. Continue.

Step 2: Go to child.__proto__ → parent → { greet: function }
         Found "greet"! → return the function  ✅

Lookup for child.toString:

Step 1: Look in child's own properties → { name: "Parth" }
         Not found. Continue.

Step 2: Go to child.__proto__ → parent → { greet: function }
         Not found. Continue.

Step 3: Go to parent.__proto__ → Object.prototype → { toString, hasOwn, ... }
         Found "toString"! → return the function  ✅

Lookup for child.nonExistent:

Step 1: child → not found
Step 2: parent → not found
Step 3: Object.prototype → not found
Step 4: Object.prototype.__proto__ → null → stop!
         Return undefined  ❌

this in Inherited Methods:

⚠️ Critical: When you call an inherited method, this refers to the object the method was called ON, not the object where the method was defined. 
const parent = {
  name: "Parent",
  intro: function() { return "I am " + this.name; }
};

const child = Object.create(parent);
child.name = "Child";

parent.intro();  // "I am Parent"  — this = parent
child.intro();   // "I am Child"   — this = child (even though intro lives on parent!)

This is why the this keyword rules you learned in Chapter 4 combine so powerfully with prototypes.

5. Object.create() — Manually Setting the Prototype

▼

Object.create(proto) creates a new object with its __proto__ explicitly set to proto. It's the most direct way to establish a prototype link.

Basic Usage:

const animal = {
  eats: true,
  sleep: function() { return "zzz"; }
};

const dog = Object.create(animal);
dog.barks = true;

console.log(dog.barks);        // true       (own property)
console.log(dog.eats);         // true       (inherited)
console.log(dog.sleep());      // "zzz"      (inherited method)
console.log(dog.__proto__);    // animal object
console.log(dog.__proto__ === animal);  // true

Chaining Prototypes with Object.create():

const animal = { eats: true };
const dog = Object.create(animal);      // dog.__proto__ = animal
dog.barks = true;

const puppy = Object.create(dog);       // puppy.__proto__ = dog
puppy.cute = true;

// The chain:
puppy → dog → animal → Object.prototype → null

puppy.cute;   // true  (own)
puppy.barks;  // true  (from dog)
puppy.eats;   // true  (from animal)

Visualized Chain:

┌────────┐   ┌──────┐   ┌────────┐   ┌──────────────────┐   ┌──────┐
│ puppy  │──→│ dog  │──→│ animal │──→│ Object.prototype │──→│ null │
│ cute   │   │ barks│   │ eats   │   │ toString, ...    │   │      │
└────────┘   └──────┘   └────────┘   └──────────────────┘   └──────┘
💡 Object.create(null) Creates a Pure Object:
const bare = Object.create(null);
This creates an object with NO prototype at all — not even Object.prototype. Useful for creating dictionaries where you don't want keys like toString to accidentally collide with inherited methods.

⭐ 6. The new Keyword — What It Actually Does

▼
⭐ This is one of the most-asked JavaScript interview questions. "Explain what new does under the hood." If you can explain the 4 steps below, you're ahead of 95% of candidates.

The Constructor Function Pattern:

function Person(name) {
  this.name = name;
}
Person.prototype.greet = function() {
  return "Hi, I'm " + this.name;
};

const p = new Person("Parth");
console.log(p.name);         // "Parth"
console.log(p.greet());      // "Hi, I'm Parth"

What new Does — The 4 Steps:

When you write new Person("Parth"), the engine executes these 4 steps:

StepWhat Happens
1Creates a brand new empty object: {}
2Sets the new object's __proto__ to Person.prototype
3Calls Person with this bound to the new object (passing "Parth" as name)
4Returns the new object (implicitly — you don't write return)

The 4 Steps — Visualized:

Step 1: Create empty object
        ┌──────────────┐
        │ newObj: {}   │
        └──────────────┘

Step 2: Link __proto__ to Person.prototype
        newObj.__proto__ = Person.prototype;

        ┌──────────────┐        ┌──────────────────┐
        │ newObj: {}   │───────→│ Person.prototype │
        │ __proto__    │        │ ├── greet: fn    │
        └──────────────┘        └──────────────────┘

Step 3: Call Person.call(newObj, "Parth")
        // Inside Person: this = newObj
        // this.name = "Parth" → sets newObj.name = "Parth"

        ┌───────────────────────┐        ┌──────────────────┐
        │ newObj:               │───────→│ Person.prototype │
        │ ├── name: "Parth"     │        │ ├── greet: fn    │
        │ └── __proto__         │        └──────────────────┘
        └───────────────────────┘

Step 4: Return newObj
        p = newObj;

Doing It Manually (Without new):

You can replicate what new does with plain code. This proves there's no magic:

// This:
const p = new Person("Parth");

// Is EQUIVALENT to:
const p = {};                                    // Step 1
Object.setPrototypeOf(p, Person.prototype);      // Step 2
Person.call(p, "Parth");                         // Step 3
// (Step 4: return happens automatically since we already have p)

Why All Instances Share Methods (Q4 Answer):

const p1 = new Person("Parth");
const p2 = new Person("Deepika");

console.log(p1.greet === p2.greet);   // true ✅

// Why? Because greet is NOT on p1 or p2. It lives on Person.prototype.
// Both p1 and p2 look up "greet" via their __proto__, which points to
// the SAME Person.prototype object. Same function reference. Same memory.

MEMORY:
┌─────────────────┐        ┌──────────────────────┐
│ p1: {name}      │───────→│ Person.prototype     │
├─────────────────┤        │ └── greet: fn (ONE   │
│ p2: {name}      │───────→│                copy) │
└─────────────────┘        └──────────────────────┘

If greet lived on each instance, we'd waste memory.
Prototypes let 1000 instances share 1 function.
⚠️ Forget new = Silent Bug: 
const p = Person("Parth");   // no `new`!
console.log(p);              // undefined
// Person was called as a regular function.
// `this` was window (or undefined in strict mode).
// It set window.name = "Parth" — a silent global pollution!
This is why capitalized functions signal "call me with new."

⭐ 7. Classes Are Just Syntactic Sugar

▼
🧠 THE breakthrough insight for anyone who's ever said "I don't get JS classes":

A class in JavaScript is not a new construct. It's syntactic sugar over the constructor function + prototype pattern you just learned. Under the hood, they compile to the exact same thing.

Proof — Class vs Constructor Function Are Identical:

Using class:

class Animal {
  constructor(name) {
    this.name = name;
  }
  speak() {
    return this.name + " makes a sound";
  }
}

const a = new Animal("Dog");

Using the constructor function pattern (what it becomes internally):

function Animal(name) {
  this.name = name;
}
Animal.prototype.speak = function() {
  return this.name + " makes a sound";
};

const a = new Animal("Dog");

Both produce the exact same result:

  • A function called Animal
  • With a prototype property containing speak
  • That you invoke with new to create instances

Proof from typeof:

class Animal { }
console.log(typeof Animal);   // "function"  ← NOT "object", NOT "class"!

// Classes ARE functions under the hood.

Proof from the Prototype Chain:

class Animal {
  speak() { return "hi"; }
}
const a = new Animal();

console.log(a.__proto__ === Animal.prototype);        // true ✅
console.log(Animal.prototype.speak === a.speak);      // true ✅
console.log(a.__proto__.__proto__ === Object.prototype); // true ✅

// Same chain. Same mechanism. Just prettier syntax.

Why Did They Add Classes Then?

  1. Familiarity for developers coming from Java, C++, Python, etc.
  2. Cleaner syntax — one block instead of function + multiple prototype assignments
  3. Cleaner inheritance — extends is way nicer than manually chaining prototypes
  4. Enforced new — calling a class without new throws an error (safer than constructor functions)
🎯 The Bottom Line: A class in JS is just a nicer syntax for the prototype pattern. It adds no new capability, no new inheritance model. If you understand prototypes, you understand classes. If someone tells you "JS uses classical inheritance now" — they're wrong. JS uses prototypal inheritance, with a class-looking coat of paint.

Side-by-Side Feature Comparison:

FeatureClass SyntaxConstructor Function
Define constructorconstructor(name) {...}function Animal(name) {...}
Add methodspeak() {...}Animal.prototype.speak = function() {...}
Instantiatenew Animal("Dog")new Animal("Dog")
Inheritclass Dog extends AnimalManual: Dog.prototype = Object.create(Animal.prototype)

Forget newTypeErrorSilent global pollution

8. extends, super & instanceof

▼

Inheritance with extends:

class Vehicle {
  constructor(type) {
    this.type = type;
  }
  describe() {
    return "This is a " + this.type;
  }
}

class Car extends Vehicle {
  constructor(brand) {
    super("car");       // MUST call super() first in derived class
    this.brand = brand;
  }
  showBrand() {
    return this.describe() + " made by " + this.brand;
  }
}

const c = new Car("Toyota");
console.log(c.showBrand());  // "This is a car made by Toyota"

What super() Does:

super("car") calls the parent class's constructor (Vehicle) with this bound to the new Car instance. So Vehicle's this.type = "car" ends up setting the property on the Car instance.

⚠️ In derived class constructors, you MUST call super() BEFORE using this. If you don't, you'll get a ReferenceError. This is because this isn't initialized until super() runs.

The Prototype Chain with extends:

const c = new Car("Toyota");

CHAIN:
┌─────┐   ┌──────────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌──────┐
│  c  │──→│ Car.prototype│──→│ Vehicle.prototype│──→│ Object.prototype │──→│ null │
└─────┘   │ ├── showBrand│   │ └── describe     │   │ ├── toString     │   └──────┘
          └──────────────┘   └──────────────────┘   └──────────────────┘

// Property lookups walk up this chain:
c.brand        → found on c
c.showBrand()  → found on Car.prototype
c.describe()   → found on Vehicle.prototype
c.toString()   → found on Object.prototype

instanceof — Checking the Chain:

c instanceof Car        // true
c instanceof Vehicle    // true (because Vehicle.prototype is in the chain)
c instanceof Object     // true (because Object.prototype is in the chain)

// How it works internally:
// x instanceof Y  →  Is Y.prototype anywhere in x's prototype chain?

Key Chain Relationships:

c.__proto__ === Car.prototype                       // true
Car.prototype.__proto__ === Vehicle.prototype       // true
Vehicle.prototype.__proto__ === Object.prototype    // true
Object.prototype.__proto__ === null                 // true
💡 The chain traverses .prototype objects, NOT the classes themselves. A common confusion: writing "c → Car → Vehicle" as if the classes were part of the chain. They're not. The classes are functions. The chain is built from the prototype objects of those classes.

9. Extending Built-in Prototypes (Polyfills)

▼

You can add methods to built-in prototypes like Array.prototype, String.prototype, or Function.prototype. Every existing and future instance instantly gets the new method through the chain.

Example — Adding a Custom Array Method:

Array.prototype.first = function() {
  return this[0];
};

// Now every array in your codebase has this method:
[1, 2, 3].first();              // 1
["a", "b", "c"].first();        // "a"

Example — Writing a Polyfill for bind:

// If a browser didn't support Function.prototype.bind (very old IE), we could add it:
Function.prototype.myBind = function(context, ...args) {
  const originalFn = this;
  return function(...remainingArgs) {
    return originalFn.apply(context, [...args, ...remainingArgs]);
  };
};

// Every function now has myBind:
function greet(greeting, name) { return greeting + ", " + name; }
const boundGreet = greet.myBind(null, "Hello");
boundGreet("Parth");   // "Hello, Parth"

This is called a polyfill — code that provides a modern feature in older environments where it doesn't exist natively. Writing a polyfill for bind, call, apply, or array methods like map/filter/reduce is a very common interview question.

⚠️ Warning — Don't Do This in Production:

Modifying built-in prototypes is dangerous:
  • Naming collisions: If your Array.prototype.first conflicts with a future JS spec addition, chaos ensues.
  • Third-party library conflicts: Another library might add the same method with different behavior.
  • Debugging nightmares: Someone reading your code has no idea where arr.first() came from.
  • Performance: Some engines can't optimize modified built-ins as aggressively.
Use utility functions or wrapper classes instead. Extending built-in prototypes is fine for learning, polyfills for real missing features, or writing frameworks — but not for regular application code.

10. Common Gotchas & Pitfalls

▼

Gotcha A: Shadowing (Instance Beats Prototype)

If you set a property directly on an instance with the same name as one on its prototype, the instance version wins during lookup — but the prototype version is still there.

function Bird() {}
Bird.prototype.sing = function() { return "Tweet"; };

const b1 = new Bird();
console.log(b1.sing());       // "Tweet" (from prototype)

b1.sing = function() { return "Silent"; };   // shadows on instance

console.log(b1.sing());       // "Silent" (instance wins)

// The prototype version is still there:
console.log(b1.__proto__.sing());   // "Tweet"

// Delete the shadow → prototype version returns:
delete b1.sing;
console.log(b1.sing());       // "Tweet" again

Gotcha B: Modifying Prototype at Runtime Affects Existing Instances

function Bird() {}
const b1 = new Bird();
const b2 = new Bird();

// Add a method to the prototype AFTER instances were created:
Bird.prototype.fly = function() { return "flying"; };

// Existing instances INSTANTLY have access:
b1.fly();   // "flying"  ✅
b2.fly();   // "flying"  ✅

// Because instances only hold a REFERENCE to the prototype, not a copy.
// When you modify the prototype, all instances see the change immediately.

Gotcha C: prototype vs __proto__ on the Constructor Itself

function Person() {}

// The function has BOTH:
Person.prototype     // → template object (for instances to inherit)
Person.__proto__     // → Function.prototype (because Person IS a function)

// A common confusion:
const p = new Person();
p.__proto__ === Person.prototype;   // true (this is what we care about)
p.__proto__ === Person.__proto__;   // false (unrelated)

Gotcha D: Forgetting new

function Person(name) {
  this.name = name;
}

const p = Person("Parth");   // ❌ Forgot new!
console.log(p);              // undefined
console.log(window.name);    // "Parth" — polluted the global!

With classes, this can't happen — calling a class without new throws a TypeError.

Gotcha E: hasOwnProperty() vs in

const parent = { inherited: true };
const child = Object.create(parent);
child.own = true;

child.hasOwnProperty("own");         // true
child.hasOwnProperty("inherited");   // false — not on child, only on parent

"own" in child;                      // true
"inherited" in child;                // true — `in` walks the whole chain

hasOwnProperty() checks only the object itself. in walks the entire prototype chain.

Gotcha F: Object.create(null) — No Prototype at All

const bare = Object.create(null);

bare.toString;         // undefined — no Object.prototype!
bare.hasOwnProperty;   // undefined
bare.__proto__;        // undefined

// Useful for pure dictionaries where you don't want inherited methods
// interfering with your keys.

12. Interview Answer Templates

▼

Q: "What is prototypal inheritance in JavaScript?"

"Prototypal inheritance is JavaScript's inheritance model. Every object has a hidden reference called __proto__ pointing to another object called its prototype. When you access a property that doesn't exist on the object, the engine walks up the __proto__ chain until it finds the property or reaches null. This lets one object share methods and properties with another, without copying them. It's fundamentally different from classical inheritance in languages like Java — there are no real classes, just objects linking to other objects."

Q: "What's the difference between __proto__ and prototype?"

"prototype is a property that exists only on functions. It's the template object where you attach methods that instances will inherit when you use new. __proto__ is a property on every object — it's the actual link pointing to the prototype the object inherits from. When you do new Person(), the engine sets the new instance's __proto__ to point to Person.prototype. So they're related: __proto__ is the link, prototype is what it links to. In modern code, Object.getPrototypeOf() and Object.setPrototypeOf() are the recommended replacements for __proto__."

Q: "Explain what the new keyword does under the hood."

"When you write new Person("Parth"), the engine does 4 things in order: First, it creates a brand new empty object. Second, it sets that object's __proto__ to Person.prototype, establishing the inheritance link. Third, it calls the Person function with this bound to the new object, so any assignments like this.name = ... populate the new object. Fourth, it returns that new object automatically. That's it — there's no magic. You can replicate new manually using Object.create() and .call()."

Q: "Are JavaScript classes real classes?"

"No — JavaScript classes are syntactic sugar over the constructor function and prototype pattern. Under the hood, class Foo { } creates a function Foo with its methods attached to Foo.prototype. typeof a class returns "function". JavaScript still uses prototypal inheritance — extends just sets up the prototype chain between the child's and parent's prototype objects automatically. The class syntax makes it look like classical OOP, but under the hood it's the same prototype mechanism."

Explanation of the 3 setup lines:

  • Vehicle.call(this, "car") — Inside Car's constructor, this manually calls the parent's constructor with this bound to the new Car instance. This runs this.type = "car", adding the parent's properties to the new instance. It's the pre-class equivalent of super("car").
  • Car.prototype = Object.create(Vehicle.prototype) — Sets up the prototype chain. Now Car.prototype.__proto__ points to Vehicle.prototype, so Car instances can inherit methods like getType. This is the pre-class equivalent of extends Vehicle.
  • Car.prototype.constructor = Car — Fixes a side effect. When we replaced Car.prototype with a new object, we lost the automatic constructor property that pointed back to Car. This line restores it, so c.constructor === Car works correctly.

The class version is much cleaner:

class Car extends Vehicle {
  constructor(brand) {
    super("car");
    this.brand = brand;
  }
  getBrand() { return this.brand; }
}

Same result, no manual prototype plumbing. This is why classes were added — to hide this ceremony behind cleaner syntax.
