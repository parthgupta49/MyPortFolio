## 1. What it is

Three things in one static site:

- **A portfolio**: Home, Projects, About.
- **A documentation library**: Learn. Long-form technical chapters grouped by subject, searchable,
  filterable by tag. Today there is one subject (JavaScript, published as *The JavaScript Codex*)
  with 11 chapters.
- **The engine** that turns hand-written HTML into that library at build time. This is what the
  "Custom Documentation Engine" project card refers to.

There is no backend, database or CMS. Everything is built ahead of time into static files, so any
static host can serve it.

| --- | --- | --- |

| **React 19** | UI | |

| **Inter** (variable) | Typeface | Self-hosted through `@fontsource-variable/inter`, so there's no request to Google Fonts. |
| **react-icons** | Brand and stack icons | Only the icons actually imported end up in the bundle. |

That's **5 runtime + 5 dev dependencies**, about 48 packages installed in total.

Several things that are usually libraries are hand-written here on purpose: the HTML parser, the
search, the code highlighter and the scroll-reveal animation. Each one replaced a dependency that
cost more than it gave. The reasons are in the sections below.

## 4. Routes and loading

| Path | Page | Notes |
| --- | --- | --- |
| `/` | `Home.jsx` | Ships in the main bundle. It's the landing page, so it shouldn't wait on a second request. |
| `/learn` | `Learn.jsx` | Every subject, plus search across all of them. |
| `/learn/:subject` | `Subject.jsx` | One subject's chapters, its search box and tag filter. |
| `/learn/:subject/:slug` | `Chapter.jsx` | The reader. |
| `/projects` | `Projects.jsx` | |
| `/about` | `About.jsx` | |
| `*` | `NotFound.jsx` | |

**Code splitting.** Every page except Home is its own chunk, loaded on first visit. Nav links
start downloading their page's chunk on hover or keyboard focus, so the click itself feels
instant. Each chapter's JSON is also its own chunk (`import.meta.glob` in `Chapter.jsx`), so
opening one chapter downloads that chapter and nothing else. The React runtime and the router get
their own long-lived chunks (`manualChunks` in `vite.config.js`), so a deploy that changes only
site code doesn't make returning visitors re-download React.

**Old links.** Chapters used to live at `/learn/<slug>`, before subjects existed.
`LegacyChapterRedirect` in `App.jsx` checks whether that segment is really a chapter slug and, if
so, redirects to `/learn/<subject>/<slug>`, keeping any `#hash`.

**Deep links.** `#secN` jumps to section N, `#qN` to practice question N, and `#aN` opens and
jumps to answer N. `ScrollManager` in `App.jsx` waits for the lazily loaded page to paint before
resolving the hash. Without a hash it scrolls to the top on every navigation.

**Tab titles.** Every page sets its own through `usePageTitle()` (`src/lib/title.js`): "Projects —
Parth Gupta", "<chapter> — <series>", "Page not found — Parth Gupta", and so on. Home keeps the
`<title>` from `index.html`, and each page restores it on leave. The names come from `pages.js` and
`profile.js`, so renaming a page renames its tab.

## 5. The content pipeline

```
content/<subject>/*.html ─┐
content/<subject>/series.json ─┤
                          ▼
            scripts/build-notes.mjs          (parse, clean, measure, tag)
                          │
                          ├──▶ src/content/subjects.json                   every subject + totals
                          ├──▶ src/content/<subject>/index.json            chapter list + metadata
                          └──▶ src/content/<subject>/notes/<slug>.json     one file per chapter
                          ▼
            scripts/build-search.mjs         (metadata + every section heading)
                          │
                          └──▶ src/content/search.json                     ~17 KB
                          ▼
            React (Learn, Subject, Chapter)  reads only the JSON, never the HTML
```

`npm run docs` runs both scripts. `npm run build` runs `docs` first, so a deploy can never ship
stale content.

### What the parser does, in order

`scripts/build-notes.mjs` is plain Node, about 1,300 lines, with **no npm dependencies**: it
imports only `node:fs`, `node:path` and `node:url`.

1. **Finds subjects.** Every folder under `content/` is a subject. Nothing is registered anywhere.
2. **Tokenizes** each HTML file into a tree with its own small tokenizer. `<script>`, `<style>`,
   `<button>` and `<svg>` are dropped. `<nav class="sidebar">` is read separately, for section
   order and group headings.
3. **Detects the layout.** It handles two:
   - **A, collapsible.** `<div id="secN">` with a `.section-header` and `.section-content`, plus
     a sidebar nav that supplies groups and order.
   - **B, flat.** No section wrappers, no sidebar. Sections are split at top-level `<h1>`s, ids
     are made up as `sec1…secN`, and everything goes in one "Contents" group.
4. **Reads the title block**: chapter title, summary, companion-chapter links. Any drop rules
   apply here (see *Rewrite rules and the blocklist guard* below).
5. **Emits blocks.** Each section becomes a flat list of typed blocks:

   | `t` | What it is |
   | --- | --- |
   | `p` | Paragraph |
   | `h` | Sub-heading inside a section |
   | `code` | A code sample |
   | `list` | Ordered or unordered list |
   | `callout` | A themed box. `kind` comes from the source class: `note-box`→note, `blue-box`→info, `tip-box`→tip, `warn-box`→warn, `danger-box`→danger, `purple-box`→key, `bonus-box`→bonus |
   | `table` | A table. A first row of all `<th>` becomes the header. |
   | `question` | A practice question: number `n`, `difficulty` (easy, medium, hard, expert or bonus), text, optional `code` |
   | `answer` | A **marker** only (`{ t: 'answer', n: 3, html: 'Q3' }`). The answer's content is the run of blocks that follow, up to the next marker. |
   | `hr` | Divider |

   Inline formatting is kept as a **five-tag subset**: `code`, `strong`, `em`, `a`, `br`
   (`<b>` and `<i>` are mapped to `strong` and `em`). Everything else is reduced to text. That
   subset is all the renderer ever has to handle.
6. **Section headings.** A leading emoji becomes a `badge`: ⭐ is "Key idea", ⚠ is "Common
   pitfall", ⚙ is "How it works". The emoji itself is removed from the title.
7. **Measures and checks.** It numbers sections, slugifies titles, counts words (reading time is
   words ÷ 200, rounded up), counts code samples and questions, and checks that **every source
   `<pre>` came out as exactly one code sample**. A mismatch is printed as a warning, so a block
   the parser silently dropped can't hide in the totals.
8. **Derives tags** from the subject's vocabulary, or infers them if there isn't one (the full
   explanation is in the README under *How tags work*). Score per tag = title hits × 10 + section
   title hits × 6 + body hits × 1, times the entry's `weight`. A chapter keeps its top 3–5 tags
   above a floor.
9. **Writes the JSON**, then the build prints a per-chapter table: layout, sections, code
   (emitted/source), questions, words, minutes, tags.

A chapter file looks like this (trimmed):

```json

  "subject": "javascript",

  "title": "Closures in JavaScript",
  "chapterLabel": "Chapter 3",

  "video": null,
  "groups": [{ "label": "Core Concepts", "sectionIds": ["sec1", "sec2", "sec3", "sec4", "sec5"] }],
  "sections": [
    {
      "id": "sec1",
```

### Rewrite rules and the blocklist guard

The top of `build-notes.mjs` (section 1) has two tools for keeping something out of the published
site.

**Rewrite rules** change source text on its way into the JSON. They're declarative, so a newly
added chapter is cleaned by the same table:

- **drop rules** remove whole lines from a chapter's title block;
- **prose rules** rewrite specific sentences so they still read naturally (never just deleting a
  word and leaving a broken clause);
- **code rules** rename sample data consistently, including the `// → value` comments.

All three tables are empty today, because the source chapters are already written the way the site
shows them. The build prints how often each rule fired, when there are any.

<a id="blocklist-guard"></a>**The blocklist guard** re-scans every generated file at the end of the
build and **fails the build** if any blocked term appears. The terms live in `content/.blocklist`
(one per line, `#` for comments), which is **gitignored**, so the repository never has to name
what it keeps out. Without that file, on Vercel for example, the guard is skipped and the build
says so. The source is clean either way; the guard is a local safety net for new chapters.

### HTML entities

Authored HTML writes a literal `&` as `&amp;` and a literal `<` as `&lt;`. The parser must **keep**
those escaped inside `html` fields, because decoding `&lt;` there would turn text into a tag.
Decoding happens exactly where markup becomes words:

- `src/lib/inline.jsx`, which turns an `html` string into React elements, decodes text and `href`s;
- `scripts/build-search.mjs` decodes everything it writes, because the index is plain text (card
  summaries, `document.title`, the search haystack).

Both use `src/lib/entities.js`: named, decimal and hex entities in **one pass**, so `&amp;lt;`
correctly becomes the text `&lt;` rather than being decoded twice into `<`. Unknown entities are
left exactly as written. Missing this step is how `Event Loop &amp; Callback Queue` once reached a page,
raw entity and all.

**The site never injects authored HTML.** There is no `dangerouslySetInnerHTML` on content: every
element on a chapter page is built by React from the block model and the five inline tags.

## 7. Search

Two pieces: `scripts/build-search.mjs` writes the index at build time, and `searchChapters()` in
`src/lib/search.js` runs in the browser on every keystroke (React's `useDeferredValue` keeps typing
smooth).

**What's indexed:** subject metadata, chapter metadata (title, summary, tags, counts), and **every
section heading**. Section headings matter because the terms people search for, such as "TDZ",
"microtask" or "mark and sweep", are section titles, not chapter titles. Body text is **not**
indexed: that would mean shipping the whole library to the browser to power one search box. The
index is about **17 KB**.

**Scoring.** For each search term, a chapter scores:

| Where the term appears | Points |
| --- | --- |
| Chapter title, at the start | 40 |
| Chapter title, elsewhere | 28 |
| Tags | 18 |
| Section title (each one that matches) | 12 |
| Subject name (so "javascript" finds JS chapters) | 10 |
| Summary | 8 |

Results are sorted by score, then subject, then chapter order. Each result carries up to 4 matching
section headings, rendered as links straight to `#secN`.

The four questions worth being able to answer:

- **Why weighted?** Where a word appears says how much the chapter is *about* it. A chapter titled
  "Closures" is a better answer to "closures" than one that mentions closures in a summary. The
  weights encode that order: title, then tags, then section headings, then summary.
- **Why AND-based matching?** Every term must match *somewhere* in a chapter, or that chapter
  drops out. So adding a word narrows the results ("closure loop" means chapters about both),
  which is what people expect from a search box. With OR, every extra word would widen the
  results.
- **Why tags?** Tags are a curated vocabulary per subject (`series.json`), so the same concept
  always gets the same tag across chapters. They drive the filter chips. Selecting several chips
  is also AND: a chapter must carry every selected tag. In search, a tag hit scores high because a
  tag means the chapter is substantially about that thing.
- **Why not fuzzy?** These are technical terms. Fuzzy matching would make `this` match "the",
  "his" and almost everything else, and turn `map` into `max`. Matching is a plain lowercase
  substring check. It's predictable, and in a technical reference predictable matters more than
  forgiving typos.

**Why not a search library?** Lunr, Fuse.js or FlexSearch would each add more code than this
whole function (about 70 lines), and their main features (fuzzy matching, full-text
stemming) are the wrong behaviour for this content. The corpus is small enough to search
linearly on every keystroke with no noticeable cost.

## 8. Images

`scripts/optimize-images.mjs` (`npm run images`) turns source images into **AVIF + WebP + JPEG**
at the sizes actually rendered, at 1× and 2×:

| Job | Source | Widths | Crop |
| --- | --- | --- | --- |
| Portrait | `src/assets/ParthGupta_2.jpg` | 320, 640 | Square, **centre** crop |
| Project screenshots | `src/assets/projectImages/*.png` | 400, 800, 1200 | 16:10, **top** crop, so the page header survives. Only the lead card requests 1200: it spans the full row on tablets. |
| Gallery | `src/assets/gallery/*.jpg` | 500, 1000, 1600 | **None**: the original shape is kept. The 4:3 tiles are cropped by CSS, and the full-screen view shows the whole image. |

Output goes to `src/assets/optimized/` and **is committed**, so `npm run build` never needs sharp.
The script is deterministic: re-running it leaves unchanged images byte-identical.

**Don't use sharp's `attention` crop on a portrait.** It picks the highest-contrast region, which
on a face against a white backdrop pulls toward the hair and glasses and crops unevenly. That's
what once pushed the hero portrait visibly to the right inside its circle.

`src/components/Picture.jsx` renders a `<picture>` with all three formats, and the browser picks
the best one it supports. Images load lazily unless marked `priority` (the hero portrait).
Unreferenced images are never bundled.

## 9. Theming and motion

**Themes.** Both are sets of CSS custom properties on `<html data-theme="dark|light">`, defined in
`src/index.css`. A tiny inline script in `index.html` picks the theme **before first paint**:
whatever is saved in `localStorage` under `theme`, otherwise the OS preference. Without it, every
load would paint the default theme and then visibly switch. `src/lib/theme.jsx` reads what that
script decided rather than deciding again, and saves the visitor's choice when they toggle.

**Motion is CSS only.** Scroll reveals use **one shared** `IntersectionObserver`
(`src/lib/reveal.jsx`) that adds the class `is-in`, and CSS runs the transition. Each element stops
being observed once it has appeared. That replaced framer-motion, react-spring and two typing
libraries. The wordmark dot's pulse is a soft opacity fade rather than a hard blink, because a true
blink reads as a rendering fault. Everything respects `prefers-reduced-motion`.

## 10. Social previews, SEO and hosting

**Social previews** (LinkedIn, X, Slack, WhatsApp) need an *absolute* URL for the preview image,
because the crawler fetches the HTML on its own with no page to resolve a relative path against.
The deployed address can't be known when writing `index.html`, and a guessed domain is worse than
none. So `index.html` contains the placeholder `%SITE_URL%`, and the `absoluteUrls()` plugin in
`vite.config.js` fills it in at build time from the first of these that is set:

1. `SITE_URL`, which you set yourself (use this for a custom domain);
2. Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, then `VERCEL_URL`;
3. Netlify's `URL`, then `DEPLOY_PRIME_URL`;
4. Cloudflare Pages' `CF_PAGES_URL`.

If none is set (a local build, for example), the plugin **removes** the tags that need an absolute
URL, including `og:image:width/height/alt`, and switches `twitter:card` from `summary_large_image`
to `summary`, so the page never advertises an image it can't serve. The preview image itself is
`public/og.png`, generated by `npm run og` from the name, role and the dark theme's colours.

**Single-page app hosting.** There is one real HTML file. Opening `/learn/javascript/closures`
directly, or refreshing it, only works because the host is told to serve `index.html` for every
path and let the router decide. `vercel.json` does that on Vercel; `public/_redirects` does it on
Netlify and Cloudflare Pages.

**SEO today.** Every route is served the same HTML shell with the same title and description.
Per-chapter titles exist only after JavaScript runs (`document.title`). Search engines that render
JavaScript will see them; link-preview crawlers won't. This is accepted for now. The fix,
prerendering, is in [ROADMAP.md](ROADMAP.md). `robots.txt` allows everything.

## 11. Accessibility

What's actually in place:

- A **"Skip to content"** link, the first focusable element on every page.
- Visible **focus outlines** in the accent colour.
- **`prefers-reduced-motion`** turns off reveals and transitions.
- **Labels** on every icon-only control: theme toggle, menu button, search boxes, lightbox
  controls.
- The current section in the Contents rail is marked with **`aria-current`**.
- The gallery requires **`alt` text** on every photo, and the lightbox works from the keyboard
  (Esc closes, ← → move between photos).
- The loading spinner is a **`role="status"`** live region with screen-reader text.
- **Colour contrast meets WCAG AA (4.5:1) for all text, in both themes**, measured on every route
  against the surface each element actually sits on. The tightest is the small "faint" text
  (labels, dates, card tags): **4.62:1** dark and **4.65:1** light. It was 3.2–4.05:1 until
  2026-11-04; the reasoning is in a comment next to `--text-faint` in `src/index.css`. The Learn
  nav link in the accent colour is about 5.5:1.
- **Heading outline** never skips a level: on Projects, the card titles are `h2` directly under the
  page's `h1` (`ProjectCard`'s `heading` prop).
- The hero's **rotating phrases** are visual only (`aria-hidden`). Screen readers get the full list
  once, from a visually hidden span.
- Evidence links in Recognition and Certifications ("View certificate ↗") name the entry they open
  and say they **open in a new tab**. They look like links at rest, not only on hover, so touch
  users can see them, and their tap target is 24px tall.

No formal audit with a screen reader or an automated tool such as axe has been done yet.

## 13. Why it's built this way

The questions in the case-study template ([PLAN.md](PLAN.md)), answered from what was actually
done.

**Why HTML as the source?** The chapters already existed as hand-written HTML, with real structure:
callouts, grouped sidebars, practice sheets, answer keys. Compiling that HTML kept all 11 chapters
as they were, with no rewrite. Authors keep full control of how a chapter is written; the parser
only cares about structure (class names and tags), never styling.

**Why not Markdown?** It would have meant converting every chapter, then inventing custom syntax
for callouts, difficulty-tagged questions and numbered answers (through MDX or directive plugins,
which bring their own dependency stack). HTML already expresses that structure with plain class
names.

**Why compile to JSON instead of rendering the HTML?**

- **Safety.** No authored markup is ever injected into the page. React builds every element from a
  small, known set of block types.
- **Consistency and theming.** Every chapter looks the same and follows the light/dark theme,
  whatever CSS its source file had.
- **Checking before shipping.** The build measures and validates everything up front: counts,
  dropped code blocks, tags, blocklisted terms. A bad chapter fails the build instead of
  shipping.
- **Speed.** Each chapter is one small lazily loaded chunk, and the search index is built from the
  same data.

**Why not Docusaurus (or VitePress, Nextra)?** They're whole site frameworks. Using one meant
either running two sites (portfolio + docs) or rebuilding the portfolio inside the framework's
routing and theme. It would also add hundreds of packages, against a project that went from
1,854 to 47. The answer-key behaviour (collapsible answers paired to questions by number) would
still have needed custom plugins.

**Why build custom search?** See [section 7](#7-search): the index is small, the ranking rules are
specific, and fuzzy matching is wrong for technical terms.

**Why a hand-written code highlighter?** Shiki and Prism are 100 KB+ and support around 200
languages. Every sample so far is JavaScript. The tokenizer is about 1 KB. Its limitation is listed
below.

## 14. Known limitations

Honest list. Each one is either accepted for now or tracked in [ROADMAP.md](ROADMAP.md).

- **No automated tests.** The parser was verified by hand: content diffed against the source,
  and route sweeps for raw entities, broken text and empty states. The current totals are the
  baseline a future test should lock in: **11 chapters, 184 sections, 1,910 blocks, 579 code
  samples (495 standalone + 84 inside practice questions), 92 questions, 92 answers, 228 minutes of
  reading, 17.1 KB search index.**
- **Shared HTML shell for SEO.** See [section 10](#10-social-previews-seo-and-hosting).
- **The highlighter only knows JavaScript.** A subject with Python, SQL or shell samples would be
  coloured as if it were JavaScript. Extend `src/lib/highlight.js` (or swap in a library) before
  publishing a non-JS subject.
- **Search doesn't read body text**, only titles, tags, summaries and section headings.
